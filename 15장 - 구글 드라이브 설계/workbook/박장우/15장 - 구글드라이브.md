# 요구사항
---
> [!quote] 1단계 문제 이해 및 설계 범위 확정
> **지원자**: 가장 중요하게 지원해야 할 기능들은 무엇인가요?
> **면접관**: 파일 업로드/다운로드, 파일 동기화, 그리고 알림(notification)입니다.
>
> **지원자**: 모바일 앱이나 웹 앱 가운데 하나만 지원하면 되나요, 아니면 둘 다 지원해야 합니까?
> **면접관**: 둘 다 지원해야 합니다.
>
> **지원자**: 파일을 암호화해야 할까요?
> **면접관**: 네.
>
> **지원자**: 파일 크기에 제한이 있습니까?
> **면접관**: 10GB 제한이 있습니다.
>
> **지원자**: 사용자는 얼마나 됩니까?
> **면접관**: 일간 능동 사용자(DAU) 기준으로 천만(10Million) 명입니다.

## 기능 요구사항
1. 파일 업로드: 드래그 앤 드롭으로 파일을 추가한다. 파일 하나는 최대 10GB.
2. 파일 다운로드
3. 여러 단말 동기화: 한 단말에서 파일을 추가하거나 고치면 다른 단말에도 자동으로 반영된다.
4. 파일 갱신 이력 조회 (revision history)
5. 파일 공유
6. 알림: 파일이 편집, 삭제, 공유되면 관련 사용자에게 알린다.
7. 지원 단말: 웹, 모바일 앱
8. 파일 암호화

제외: 구글 문서처럼 여러 사람이 한 문서를 동시에 편집하는 기능

## 비기능 요구사항
1. 안정성: 데이터를 절대 잃어버리면 안 된다.
	- 내구성. 서버나 데이터센터가 통째로 날아가도(DR) 복구할 수 있게 하라는 것
2. 빠른 동기화: 동기화가 느리면 사용자가 떠난다.
3. 네트워크 대역폭 절약: 모바일 데이터 요금제를 쓰는 사용자에게 특히 중요하다.
	- 파일을 통째로 주고받지 말라는 것. 
4. 규모 확장성: 트래픽이 아주 많아도 처리할 수 있어야 한다.
	- 서버만 늘리면 버티는 구조
5. 높은 가용성: 일부 서버가 죽거나 느려지거나 네트워크 일부가 끊겨도 계속 쓸 수 있어야 한다.
	- 서비스가 멈추지 않게 하라는 것. 한 대가 죽어도 다른 대가 이어받도록 모든 구성 요소를 이중화하고 장애 조치(failover)를 자동으로 한다.

## 규모
| 항목      | 값                                     |
| ------- | ------------------------------------- |
| 사용자     | 가입 5천만 명, DAU 천만 명                    |
| 저장 공간   | 사용자마다 10GB, 전체 최대 500PB               |
| 업로드     | 사용자마다 하루 2개, 평균 500KB                 |
| 업로드 QPS | 천만 x 2 / 86,400초 = 약 240, 최대 480      |
| 하루 유입량  | 천만 x 2 x 500KB = 10TB (1년이면 약 3.65PB) |

500PB는 모두가 10GB를 꽉 채웠을 때의 상한이다. 실제로 쌓이는 속도는 하루 10TB 정도다.

# 읽기 전의 개발
---
## 1단계: 업로드와 다운로드
---
로드밸런서 뒤에 API 서버 여러 대를 둔다. 파일은 S3에, 파일 정보(이름, 주인, S3 키)는 DB 한 대에 둔다. 파일은 요청 하나로 통째로 전송한다.

![[구글드라이브-1단계.svg]]

- 업로드: S3에 파일을 다 올린 다음 DB에 기록한다. 거꾸로 하면 없는 파일을 가리키는 행이 생길 수 있다.
- 다운로드: DB에서 S3 키를 찾아 S3에서 파일을 가져온다.
- S3를 쓴 이유: 서버마다 디스크를 두면 다른 서버에서는 그 파일을 찾을 수 없다. 디스크 하나만 두면 그 디스크가 죽을 때 파일을 전부 잃게 된다. S3는 주소는 하나인데 안에서 여러 데이터센터에 복제한다.

문제는 10GB 파일이다. LTE 10Mbps면 올리는 데 2시간 넘게 걸린다.

### 문제점
1. 끊기면 처음부터 다시 올린다.
2. 로드밸런서의 요청 크기 제한에 걸린다.
3. 업로드 하나가 서버 스레드를 몇 시간씩 점유한다.
4. 모든 바이트가 API 서버를 거친다.
5. S3는 PUT 한 번에 5GB까지만 허용한다.
6. DB가 SPOF라 죽으면 전체가 멈춘다. (나중 단계)

## 2단계: 8MB part로 나눠 올리기
---
1단계 문제점 1, 2, 3, 5번은 10GB를 요청 하나로 통째로 보내서 생긴다. 파일을 8MB part로 나눠 따로 올리고, 마지막에 S3가 합친다(S3 멀티파트 업로드).

![[구글드라이브-2단계.svg]]

- `POST /uploads` : 업로드를 시작한다. S3에서 업로드 id를 받고, DB에 업로드 진행 중으로 기록한다.
- `PUT /uploads/{id}/parts/{n}` : part 하나를 올린다. 어느 API 서버로 가도 된다.
- `GET /uploads/{id}` : 끊긴 뒤 받은 part 번호를 확인하고, 빠진 part만 다시 보낸다.
- `POST /uploads/{id}/complete` : S3가 part를 합치고, DB의 업로드 상태를 완료로 바꾼다.
- 다운로드는 HTTP Range 헤더로 구간을 나눠 요청한다.

8MB는 아래를 보고 정한다.
- S3 part 제약: 최소 5MB, 최대 10,000개
- 파일 최대 크기: 10GB
- 너무 작을 때: 요청 수가 많아져 왕복 시간, 인증 횟수, S3 요청 요금이 증가한다
- 너무 클 때: 느린 망에서 끊기면 다시 보내야 하는 양이 많고, 요청 하나가 오래 걸린다

### 문제점
1. 모든 바이트가 API 서버를 거친다. (1단계 4번)
2. 중간에 포기한 업로드의 part가 S3에 남아 비용이 나간다.
3. DB가 SPOF라 죽으면 전체가 멈춘다. (나중 단계)

## 3단계: S3와 직접 주고받기 (presigned URL)
---
2단계 문제점 1번은 파일 바이트가 API 서버를 거쳐서 생긴다. API 서버는 presigned URL만 발급하고, 파일 전송은 웹/앱과 S3 사이에서 직접 일어난다. presigned URL은 API 서버가 서명한 임시 URL이다. 정해진 시간 동안 그 part 하나만 올릴 수 있다.

![[구글드라이브-3단계.svg]]

업로드 흐름 (800MB 파일, part 8MB)
1. 웹/앱이 `POST /uploads`로 업로드를 시작한다. API 서버는 S3에서 uploadId를 받고, DB에 업로드 진행 중으로 기록한다.
2. API 서버가 part 100개의 presigned URL을 서명해서 돌려준다. URL 안에 uploadId와 part 번호가 들어 있다. 서명은 API 서버가 직접 계산하므로 S3 호출이 없다.
3. 웹/앱이 URL마다 part를 S3에 직접 PUT하고, 응답으로 받은 ETag를 모은다.
4. 웹/앱이 `POST /uploads/{id}/complete`를 보낸다. API 서버는 S3에 part 합치기를 요청하고, 크기를 확인한 뒤 DB의 업로드 상태를 완료로 바꾼다.

다운로드 흐름
1. 웹/앱이 `GET /files/{id}`로 다운로드용 presigned URL을 요청한다.
2. 웹/앱이 S3에 Range로 구간을 나눠 직접 요청한다.

- 끊긴 뒤에는 받은 part를 확인하고, 빠진 part의 URL을 다시 받아 올린다.
- URL은 만료 시간을 짧게 둔다(예: 15분). 새 나가면 만료 전까지 다른 사람도 올릴 수 있다. 10GB처럼 오래 걸리는 파일은 URL을 나눠서 발급한다.
- complete 때 S3의 실제 크기를 확인한다. 웹/앱이 알린 크기보다 크게 올릴 수 있다.

### 문제점
1. 중간에 포기한 업로드의 part가 S3에 남아 비용이 나간다. (2단계 2번)
2. DB가 SPOF라 죽으면 전체가 멈춘다. (나중 단계)

## 4단계: 변경 기록과 알림 서버 (long polling)
---
여러 단말 동기화를 다룬다. 폴링은 요청이 너무 많고 반영이 늦다. 그래서 바뀐 게 생기면 알림 서버가 알려 준다.

![[구글드라이브-4단계.svg]]

1. 폰이 알림 서버에 long polling으로 대기한다. 마지막으로 본 변경 번호(커서)를 같이 보낸다.
2. 노트북이 업로드를 끝내면 API 서버가 DB에 변경 기록을 쓰고 알림 서버에 알린다.
3. 알림 서버가 폰에 변경이 있다고 응답한다.
4. 폰이 API 서버에 커서 이후 변경 목록을 요청하고, 바뀐 파일을 S3에서 가져온다.

- 알림 서버는 API 서버와 따로 두고 논블로킹으로 구현한다. 연결을 오래 유지해도 스레드를 점유하지 않는다.
- 앱이 백그라운드에 있으면 FCM/APNs 푸시로 알린다.

> [!note]- 서버가 클라이언트에 먼저 보내는 방법
> | 방식 | 동작 | 서버가 보낼 수 있는 때 | 단점 |
> | --- | --- | --- | --- |
> | Polling | 정해진 간격마다 요청한다 | 요청이 왔을 때 | 바뀐 게 없어도 요청이 오고, 간격만큼 늦다 |
> | Long Polling | 서버가 변경이나 타임아웃까지 응답을 미룬다. 응답을 받으면 다시 요청한다 | 걸려 있는 요청이 있을 때 | 응답마다 다시 요청한다 |
> | SSE | 서버가 HTTP 응답을 닫지 않고 이벤트를 이어서 보낸다 | 아무 때나 (서버 → 클라이언트만) | HTTP/1.1이면 브라우저에서 도메인당 연결 6개 제한 |
> | WebSocket | HTTP 연결을 업그레이드한 뒤 양쪽이 메시지를 보낸다 | 아무 때나 (양방향) | HTTP 요청 단위가 아니라 로드밸런서, 배포 처리를 따로 챙겨야 한다 |
>
> - 동기/비동기는 방식이 아니라 서버 구현(블로킹/논블로킹)으로 갈린다.
> - Long Polling, SSE, WebSocket은 연결을 오래 유지한다. 동기 MVC(Tomcat 기본)는 요청 하나가 워커 스레드 하나를 응답까지 점유하고, 워커는 최대 200개다. 60초씩 기다리는 연결이 200개만 들어와도 다른 요청을 받지 못한다.
> - 앱이 백그라운드에 있으면 OS가 연결을 유지해 주지 않는다. 그래서 FCM/APNs 푸시를 쓴다.
> - 4단계는 Long Polling을 골랐다. 변경이 드물고 양방향이 필요 없다.
>
> Spring에서는 아래 셋 중 하나로 만든다.
>
> | 방법 | 기다리는 동안 | 특징 |
> | --- | --- | --- |
> | MVC + DeferredResult | 워커를 풀에 돌려준다 | 기다리는 부분만 바꾸고 나머지는 보통 MVC 코드다. SSE는 SseEmitter |
> | MVC + 가상 스레드 | OS 스레드를 반납한다 | 코드를 바꾸지 않고 JPA도 그대로 쓴다. Java 21 이상, 24 미만은 synchronized 안에서 기다리면 OS 스레드를 점유한다 |
> | WebFlux + Netty | 콜백 객체만 유지한다 | 연결당 메모리가 가장 작다. 코드 전체를 Mono/Flux로 쓰고, JPA 대신 R2DBC를 쓴다 |
>
> MVC 두 방법은 Tomcat 연결 상한(maxConnections, 기본 8192)을 올려야 한다.

API 서버는 A의 연결이 어느 알림 서버에 있는지 모른다. 그래서 Redis Pub/Sub에 사용자별 채널을 둔다. A의 대기 요청을 가진 알림 서버가 `user:A` 채널을 구독하고, API 서버는 이 채널에 발행한다. Redis는 구독한 서버에만 전달한다. 메시지를 놓쳐도 다음 long polling 때 커서로 알아챈다.

![[구글드라이브-4단계-알림전달.svg]]

### 문제점
1. 두 단말이 같은 파일을 각자 고치면 이전에 올렸던 수정본이 덮어써진다.
2. 한 글자만 고쳐도 파일 전체를 다시 올리고 다시 받아야 한다.
3. long polling은 최대 60초마다 다시 연결하고, 그때 서버가 바뀔 수 있다. 그래서 채널 구독과 해제가 계속 일어나고, 연결 200만 개 기준으로 초당 약 3.3만 번 발생한다.
4. 포기한 업로드의 part가 S3에 쌓여 비용이 나간다. DB와 Redis가 SPOF다. (나중 단계)

## 5단계: 충돌 처리, 갱신 이력, 버킷 채널
---
4단계 문제점 1번(동시 수정)과 3번(구독 변경)을 고친다.

### 충돌과 갱신 이력
파일을 덮어쓰지 않고 버전마다 행(S3 키, 올린 기기, 시각)을 추가한다. S3 키는 업로드마다 새로 생성한다.

![[구글드라이브-5단계-충돌.svg]]

1. 노트북이 편집을 시작하면 Redis에 `editing:파일id`를 TTL 60초로 기록하고, 편집하는 동안 갱신한다.
2. 같은 파일을 연 폰에는 알림 채널로 편집 중이라고 보낸다. 폰은 편집 대기를 표시하고, 저장이 끝나면 최신본을 받아 편집한다.
3. 오프라인 편집처럼 그래도 겹치면, complete에 보낸 기준 버전이 현재 버전과 달라 충돌로 판단한다. 폰의 수정본은 충돌 사본으로 저장하고, 최신 받기와 나란히 비교 중에서 고르게 한다.

- 되돌리기는 옛 버전의 S3 키를 가리키는 새 버전을 추가한다. 어느 쪽을 골라도 수정본을 잃지 않는다.

### 구독 변경: 버킷 채널
사용자를 `hash(userId) % 1024`로 버킷에 나누고 채널도 버킷 단위(`bucket:517`)로 둔다. 로드밸런서는 버킷 번호로 안정 해시를 계산해 같은 버킷 사용자를 같은 알림 서버로 보낸다.

![[구글드라이브-5단계-버킷.svg]]

- 알림 서버는 들어온 사용자의 버킷을 구독하고, 2분 동안 비면 해제한다. 구독은 서버를 추가하거나 뺄 때만 바뀐다.
- API 서버는 A의 버킷 채널에 발행한다. 서버가 죽어서 놓친 변경은 커서로 알아챈다.

### 문제점
1. 한 글자만 고쳐도 파일 전체를 다시 올리고 다시 받아야 한다. 버전마다 파일 전체가 저장된다.
2. 포기한 업로드의 part가 S3에 쌓여 비용이 나간다. DB와 Redis가 SPOF다. (나중 단계)

## 6단계: 블록 단위 저장
---
5단계 문제점 1번은 파일을 통째로 저장해서 생긴다. 파일을 평균 8MB 블록으로 나눠 블록마다 S3 객체를 하나씩 두고, 버전은 블록 해시 목록으로 저장한다.

![[구글드라이브-6단계.svg]]

1. 단말이 파일을 블록으로 나누고, 블록마다 SHA-256 해시를 계산한다.
2. 해시 목록을 보내면 API 서버가 DB에 없는 해시만 골라 presigned URL을 발급한다.
3. 단말은 없는 블록만 `blocks/{hash}`로 S3에 올린다.
4. complete 때 버전 행에 해시 목록을 저장한다. 기준 버전 비교는 5단계와 같다.

- 다른 단말은 새 버전의 해시 목록을 보고, 자기에게 없는 블록만 S3에서 가져온다.
- 블록 하나는 PUT 한 번으로 올라가서 멀티파트 업로드는 더 이상 쓰지 않는다.

### 블록 경계: 내용 기반 분할
8MB 위치마다 자르면 파일 앞에 1바이트만 끼워 넣어도 뒤쪽이 전부 밀려서 모든 블록 해시가 바뀐다. 그래서 위치가 아니라 내용을 보고 자른다. 48바이트 창을 밀면서 rolling hash를 계산하고, 하위 23비트가 0인 곳에서 자른다. 블록 크기는 평균 8MB로 두고, 최소 2MB와 최대 32MB로 제한한다. 경계가 내용으로 정해지므로 끼워 넣은 곳의 블록 하나만 바뀐다.

### 안 쓰는 블록 정리: 참조 수
블록은 여러 버전이 나눠 쓰고, 업로드를 포기하면 어느 버전에도 속하지 않은 블록이 생긴다. 그래서 DB에 블록마다 참조 수를 둔다.
- URL을 발급할 때 블록 행을 참조 수 0으로 추가하고, complete 때 1씩 올린다. 버전이 보관 기간을 넘겨 지워지면 1씩 내린다.
- 배치 작업이 참조 수가 0이고 24시간 넘게 쓰이지 않은 블록을 지운다. 이미 있는 블록이라고 답할 때도 사용 시각을 갱신해서, 업로드 중에 지워지지 않게 한다.

> > [!tip] 보충: S3 복제 범위
> > S3는 기본으로 한 지역 안의 가용 영역(AZ) 여러 곳에 복제함. 그래서 데이터센터 하나가 멈춰도 파일은 그대로 있음. 지역 전체가 멈추는 경우까지 견디려면 지역 간 복제(CRR)를 따로 켜야 함. CRR은 비동기라서 지역이 멈춘 순간 막 올린 파일은 아직 복제되지 않았을 수 있음.

> [!note]- 동기화 충돌 (286쪽)
> 같은 파일을 동시에 고치면 먼저 처리된 변경이 성공하고, 나중 변경은 충돌로 표시됨. 사용자는 로컬 사본과 서버 최신 버전을 합칠지, 하나를 다른 파일로 대체할지 정함.
>
> ![[구글드라이브-책-충돌.svg]]
>
> > [!tip] 보충: 먼저 처리된 변경을 가리는 방법
> > 책은 무엇이 먼저인지 정하는 방법을 말하지 않음. 기준은 도착 시각이 아니라 어느 버전을 고쳤는지임. 클라이언트는 커밋할 때 자기가 고치기 시작한 버전(기준 버전)을 같이 보내고, 서버는 그 버전이 아직 최신일 때만 갱신함.
> >
> > ```sql
> > UPDATE file SET latest_version = 5
> > WHERE id = 42 AND latest_version = 4; -- 4는 클라이언트가 보낸 기준 버전
> > ```
> >
> > 갱신된 행이 0개면 다른 클라이언트가 v5를 먼저 기록했다는 뜻이라 충돌임.
> >
> > ![[구글드라이브-책-충돌판단.svg]]

> > [!tip] 보충: 압축 다음에 암호화하는 이유
> > 암호화한 데이터는 무작위 바이트처럼 보여서 압축되지 않음. 그래서 압축을 먼저 함. JPG, MP4처럼 이미 압축된 형식은 다시 압축해도 크기가 거의 그대로라서 건너뜀.

> > [!tip] 보충: 바뀐 블록을 찾는 방법과 위치
> > 책은 어느 블록이 바뀌었는지 찾는 방법을 말하지 않음. 블록 해시 목록 두 개를 비교하면 됨. 새 목록에서 해시가 달라진 자리가 바뀐 블록임.

> >
> > ![[구글드라이브-책-나누는곳.svg]]
>
> > [!tip] 보충: 고정 크기 블록의 약점
> > 4MB 경계는 파일 시작에서 4MB, 8MB처럼 위치로 정해짐. 내용을 제자리에서 고치면 문제가 없지만, 맨 앞에 한 글자를 끼워 넣으면 뒤쪽 내용이 전부 한 칸씩 밀려 모든 블록의 해시가 바뀜.
> >
> > 내용 기반 분할(CDC)은 위치 대신 내용을 보고 경계를 정함. 작은 창을 한 바이트씩 밀며 롤링 해시를 계산하고, 해시값의 하위 몇 비트가 모두 0인 곳에서 자름. 롤링 해시는 창에서 빠지는 바이트와 들어오는 바이트만으로 해시를 다시 계산하는 방법임. 끼워 넣은 곳의 블록만 바뀌고 뒤쪽 경계는 그대로 유지됨. 아래 그림은 블록을 4글자로 줄이고, 내용 기반 쪽은 마침표 뒤에서 자르게 단순화함.
> >
> > ![[구글드라이브-책-내용기반분할.svg]]

> [!note]- 높은 일관성 (290~291쪽)
> 같은 파일이 단말마다 다르게 보이면 안 되므로 강한 일관성이 기본임. 캐시는 DB 원본이 바뀌면 사본을 무효화함. DB는 ACID를 지원하는 관계형 DB를 고름.
>
> > [!tip] 보충: 캐시를 지우는 순서
> > DB를 먼저 갱신하고 그다음 캐시 항목을 지움. 캐시 값을 새 값으로 고치면 쓰기 두 개가 엇갈릴 때 어긋남. A가 DB에 1을 쓰고 B가 DB와 캐시에 2를 쓴 뒤, A가 늦게 캐시에 1을 쓰면 DB는 2인데 캐시는 1이 됨. 지워 두면 다음에 읽을 때 DB에서 최신 값을 가져와 캐시를 다시 채움.
> >
> > ![[구글드라이브-책-캐시무효화.svg]]

> [!note]- 메타데이터 DB (291~292쪽)

> file_version 행은 읽기 전용이라 갱신 이력이 훼손되지 않음. 블록을 block_order 순서로 합치면 그 버전의 파일이 복원됨. device의 push_id는 모바일 푸시용임.

> [!note]- 업로드 절차 (292~293쪽)
> 클라이언트 1이 메타데이터 추가와 파일 업로드를 동시에 요청함.
>
> ![[구글드라이브-책-업로드.svg]]
>
> - 메타데이터는 DB에 대기 중(pending)으로 기록하고, 클라이언트 2에 업로드 중이라고 알려 줌.
> - 블록 저장소 서버가 블록을 나눠 압축, 암호화해서 S3에 올림. 다 올라가면 S3가 API 서버에 완료 콜백을 보내고, API 서버가 상태를 완료(uploaded)로 바꾼 뒤 클라이언트 2에 완료를 알려 줌.
>
> > [!tip] 보충: 완료 콜백의 실제 구현
> > S3는 업로드가 끝났을 때 임의의 HTTP 주소를 직접 호출하지 않음. 대신 이벤트 알림을 SQS/SNS/Lambda/EventBridge로 보낼 수 있음. 책의 완료 콜백은 S3 이벤트를 SQS로 보내고 API 서버가 꺼내 처리하는 식으로 구현함.
>
> > [!tip] 보충: 블록 목록부터 커밋하는 방식
> > 드롭박스는 업로드 순서가 다름. 새 버전의 블록 목록을 먼저 서버에 보내 보고(커밋), 서버가 없다고 답한 블록만 올린 뒤 다시 커밋함. 블록이 다 올라간 다음에 새 버전이 생기므로 대기 중 상태와 완료 콜백이 필요 없고, 다른 단말이 반쯤 올라간 파일을 받을 일도 없음. 끊겨도 다시 커밋하면 서버가 아직 없는 블록만 다시 요청함. 기준 버전 비교도 이 커밋에서 함.
> >
> > ![[구글드라이브-책-업로드커밋.svg]]

> [!note]- 알림 서비스 (295~296쪽)
> 파일 수정을 다른 클라이언트에 바로 알려 충돌 가능성을 줄임. 웹소켓 대신 롱 폴링(드롭박스 방식)을 고름. 알림은 서버에서 클라이언트로 가는 한 방향이고, 자주 생기지 않으며 양도 적기 때문임.
>
> 클라이언트는 롱 폴링 연결을 유지하다가 변경이 오면 최신 내역을 다운로드하고, 다운로드가 끝나거나 타임아웃이 되면 바로 다시 요청함.
>
> ![[구글드라이브-책-롱폴링.svg]]
>
> > [!tip] 보충: 오프라인 사용자 백업 큐 대신 변경 기록과 커서
> > 백업 큐 방식은 단말마다 큐가 하나씩 필요하고, 오래 꺼져 있던 단말의 큐는 계속 쌓임. 드롭박스와 구글 드라이브 API는 변경 기록과 커서(page token)를 씀. 변경 기록에 순번을 붙여 DB에 저장하고, 단말은 마지막으로 반영한 순번(커서) 하나만 기억함. 다시 켜진 단말은 커서 이후 변경을 한 번에 요청함.
> >
> > 알림을 놓치거나 알림 서버가 죽어도 다음 요청 때 커서로 빠진 변경을 모두 가져오므로 잃는 변경이 없음. 변경 기록을 메타데이터 DB에 두면 파일 정보 변경과 같은 트랜잭션으로 묶을 수 있음.
> >
> > ![[구글드라이브-책-커서.svg]]
>
> > [!tip] 보충: 드롭박스의 롱 폴링 API
> > 드롭박스는 알림용 주소(notify.dropboxapi.com)를 따로 둠. `list_folder/longpoll`에 커서를 보내면 변경이 생기거나 타임아웃이 될 때까지 응답을 미루고, 변경이 있는지만 true/false로 돌려줌. 실제 변경 목록은 `list_folder/continue`로 가져옴.
> >
> > 타임아웃은 30~480초이고, 서버가 최대 90초의 무작위 시간을 더해 응답 시각을 흩뜨림. 클라이언트가 한꺼번에 다시 요청하지 않게 하려는 장치임. 응답에 backoff 값이 있으면 그 시간만큼 기다린 뒤 다시 요청함.

> [!note]- 저장 공간 절약 (296쪽)
> - 중복 제거: 같은 해시의 블록은 계정 단위로 한 번만 저장함.
> - 버전 정리: 보관할 버전 수에 상한을 두고, 자주 바뀌는 파일은 중요한 버전만 보관함.
> - 아카이빙 저장소: 몇 달 넘게 안 쓴 데이터는 S3 글래시어로 옮김.
>
> ![[구글드라이브-책-저장공간.svg]]
>
> > [!tip] 보충: 중복 제거를 계정 단위로 하는 이유
> > 모든 사용자를 통틀어 중복을 제거하면, 이미 있는 블록은 올리지 않아서 업로드가 바로 끝남. 그래서 업로드 시간만 보고도 남이 같은 파일을 가졌는지 알 수 있음. 2011년에는 해시만으로 드롭박스에서 남의 파일을 가져오는 도구(Dropship)가 공개되기도 했음.
>
> > [!tip] 보충: 블록을 지우는 시점과 콜드 스토리지
> > 버전을 지워도 블록은 바로 지우지 않음. 다른 버전이나 다른 파일이 같은 블록을 가리킬 수 있어서, 블록마다 참조 수를 두고 0이 된 블록만 나중에 지움.
> >
> > 콜드 스토리지로 옮기는 일은 S3 수명 주기 규칙(Lifecycle)으로 자동화할 수 있음. 글래시어는 등급에 따라 바로 꺼낼 수 있는 것부터 몇 시간이 걸리는 것까지 있음. 꺼낼 때 비용이 따로 나가고, 최소 보관 기간(90일 이상)이 있음.

> [!note]- 장애 처리 (296~298쪽)
> | 장애 | 대응 |
> | --- | --- |
> | 로드밸런서 | 부 로드밸런서가 이어서 처리함. 장애는 heartbeat로 감지함. |
> | 블록 저장소 서버 | 다른 서버가 미완료 작업을 이어서 처리함. |
> | 클라우드 저장소 | 다른 지역의 복제본에서 가져옴. |
> | API 서버 | 무상태라서 로드밸런서가 장애 서버를 제외하면 됨. |
> | 메타데이터 캐시 | 다중화하고 죽은 노드는 교체함. |
> | 메타데이터 DB | 주 서버가 죽으면 부 서버를 주 서버로 올림. 부 서버가 죽으면 다른 부 서버가 읽기를 처리함. |
> | 알림 서비스 | 서버 한 대가 연결을 100만 개 넘게 유지함. 한 대가 죽으면 100만 명이 다시 연결해야 함. 연결 100만 개를 유지할 수는 있어도 한꺼번에 새로 맺을 수는 없어서 복구가 느림. |
> | 오프라인 사용자 백업 큐 | 다중화하고, 큐가 죽으면 클라이언트가 백업 큐로 다시 구독함. |
>
> > [!tip] 보충: DB 승격과 데이터 손실
> > 주 서버가 비동기로 복제하면, 승격된 부 서버에는 주 서버가 죽기 직전에 커밋한 데이터가 없을 수 있음. 데이터를 절대 잃으면 안 되는 메타데이터 DB는 반동기나 동기 복제를 써서 커밋된 데이터가 부 서버에도 있게 함.
>
> > [!tip] 보충: 재접속 몰림 줄이기
> > 알림 서버가 죽은 뒤 클라이언트가 바로 다시 접속하면 요청이 한순간에 몰림. 재접속 전에 0~60초 사이에서 무작위로 기다리게 하면 요청이 시간에 걸쳐 흩어짐. 커서 방식이면 늦게 붙어도 놓치는 변경이 없음.
> >
> > ![[구글드라이브-책-재접속몰림.svg]]

## 4단계: 마무리 (298~299쪽)

> [!note]- 정리와 다른 선택지
> 설계는 메타데이터 관리와 파일 동기화로 나뉘고, 롱 폴링 알림 서비스가 함께 있음. 정답은 없으니 결정한 이유를 설명할 수 있어야 함.
> - 다른 선택지 1: S3에 직접 업로드하면 빠름. 대신 분할/압축/암호화를 플랫폼마다 구현해야 하고, 암호화 로직을 클라이언트에 두면 위험함.
> - 다른 선택지 2: 접속 상태 관리를 알림 서비스에서 떼어 별도 서비스로 만들면 다른 서비스도 쓸 수 있음.
>
> ![[구글드라이브-책-직접업로드.svg]]
>
> > [!tip] 보충: 블록 저장소 서버 경유와 S3 직접 업로드 비교
> > 두 방식은 파일 바이트가 어디를 지나가는지가 다름. 책 방식은 단말이 파일을 블록 저장소 서버로 보내고, 서버가 블록으로 나눠 S3에 올림. 직접 업로드는 단말이 파일을 블록으로 나누고, API 서버에서 블록마다 presigned URL을 받아 S3에 바로 올림. 이때 서버는 URL만 내주고 파일 바이트는 거치지 않음.
> >
> > **전송량과 속도**
> > - 경유: 파일이 단말에서 서버로, 서버에서 S3로 두 번 이동함. 블록을 서버가 나누므로 한 글자만 고쳐도 단말은 파일 전체를 서버로 보내야 하고, 사용자 회선을 아끼지 못함.
> > - 직접: 단말이 바뀐 블록을 골라 S3로 한 번만 보냄. 사용자 회선 사용량이 줄고 업로드도 빠름.
> >
> > **서버 부하**
> > - 경유: 모든 업로드 바이트가 블록 저장소 서버를 지나감. 10GB 업로드 하나가 서버의 대역폭과 연결을 몇 시간 차지하고, 업로드가 많아지면 서버도 그만큼 늘려야 함.
> > - 직접: API 서버는 presigned URL을 서명해서 주기만 함. 업로드 양이 많아져도 서버 부하는 거의 그대로이고, 전송은 S3가 감당함.
> >
> > **분할, 압축, 암호화를 구현하는 곳** (책이 꼽은 직접 업로드의 단점)
> > - 경유: 서버 한 곳에만 구현하면 됨.
> > - 직접: 분할과 해시 계산을 iOS, 안드로이드, 웹, 데스크톱 앱마다 구현해야 함. 다만 사용자 회선을 아끼려면 분할은 어차피 단말이 해야 함. 암호화는 단말이 하지 않고 S3 서버 측 암호화(SSE)와 HTTPS에 맡기면 되므로 단말에 키를 둘 필요가 없음. 압축은 단말의 CPU와 배터리를 쓰므로 생략하는 경우가 많음.
> >
> > **권한과 내용 확인**
> > - 경유: 서버가 요청마다 사용자를 인증하고, 받은 바이트의 해시와 크기를 직접 확인함.
> > - 직접: 업로드 권한을 presigned URL로 넘김. 블록 하나를 짧은 시간 동안만 올릴 수 있게 서명하지만, URL이 새면 만료 전까지는 누구나 쓸 수 있음. 내용 확인은 URL에 SHA-256 체크섬을 넣어 S3에 맡김. 블록 키가 해시이므로 S3가 체크섬을 확인하면 키와 내용이 맞는지도 같이 확인하는 셈임.
> >
> > **이어 올리기**
> > - 경유: 블록 저장소 서버가 업로드마다 받은 위치를 기억해야 함. 서버가 여러 대면 이어 보내는 요청이 같은 서버로 가야 해서 세션 고정이나 공유 저장소가 필요함.
> > - 직접: S3에 이미 올라간 블록은 다시 올리지 않으면 됨. 서버가 업로드 상태를 따로 기억하지 않아도 됨.
> >
> > **악성 코드 검사와 진행률** (자세한 내용은 아래 보충)
> > - 경유: 서버가 업로드 중에 내용을 보므로 바로 검사할 수 있음. 대신 검사 시간만큼 업로드가 느려짐. 진행률은 단말이 보낸 양만 알 수 있음.
> > - 직접: 서버가 업로드 중에 내용을 보지 못하므로 업로드가 끝난 뒤 따로 검사해야 함. 진행률은 블록마다 S3 응답을 받아 저장된 양으로 보여 줄 수 있음.
> >
> > **정리**
> > 사용자 회선과 서버 부하를 줄이는 게 중요하면 직접 업로드가 유리함. 업로드 중에 서버가 내용을 직접 다뤄야 하면(업로드 전에 검사, 서버에서 압축, 자체 저장소) 경유가 유리함. 나누는 위치와 전송 경로는 따로 고를 수도 있음. 드롭박스는 단말이 블록을 나누고, 바뀐 블록만 자체 블록 서버로 보냄.
>
> > [!tip] 보충: 악성 코드 검사
> > 책에는 없지만 실제 서비스는 검사함. Google Drive는 파일을 피싱과 악성 코드 기준으로 검사하고, 100MB가 넘는 파일과 일부 형식은 검사하지 못해 경고만 띄움.
> >
> > 업로드 경로에서 바로 검사하면 업로드가 검사 시간만큼 느려지고, 검사기가 멈추면 업로드도 멈춤. 블록 하나만 보고는 판단하기 어렵고, 압축과 암호화 뒤에는 내용을 볼 수 없음. 그래서 보통 커밋 뒤 비동기로 검사함.
> > 1. 커밋이 끝나면 검사 이벤트를 큐에 넣음.
> > 2. 검사 워커가 블록을 순서대로 가져와 파일 전체를 스트리밍으로 검사함.
> > 3. DB에 검사 상태(검사 중, 정상, 위험)를 기록하고, 위험이면 다운로드와 공유를 막거나 경고함.
> >
> > 블록 목록이 같은 파일은 검사 결과를 다시 씀. 서버 측 암호화는 서버가 키를 가지고 있어 복호화해서 검사할 수 있지만, 종단 간 암호화는 서버가 내용을 볼 수 없어 검사할 수 없음.
>
> > [!tip] 보충: 업로드 진행률
> > 진행률에는 단말이 보낸 양과 서버가 저장했다고 확인한 양이 있음.
> > - 책 방식처럼 파일 전체를 블록 저장소 서버로 보내면 단말은 보낸 바이트만 알 수 있음(브라우저는 XHR의 `upload.onprogress`). 다 보낸 뒤 서버가 S3에 올리는 동안은 처리 중으로 표시하고, 응답이 오면 완료로 바꿈.
> > - 서버가 확인한 양을 보여 주려면 블록마다 요청을 나누고 저장이 끝난 뒤 응답하게 함. 응답받은 블록 수가 곧 진행률임. 구글 이어 올리기도 청크마다 308과 Range 헤더로 받은 바이트를 알려 줌. 상태 조회 API(`GET /uploads/{id}`)로 저장된 블록 수를 돌려주는 방법도 있음.
> >
> > 진행률 막대에는 보낸 양을 쓰고 이어 올리기는 확인된 양을 기준으로 해서, 끊겼다가 다시 올리면 막대가 조금 뒤로 갈 수 있음.
