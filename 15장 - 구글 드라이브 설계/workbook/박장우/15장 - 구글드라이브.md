# 요구사항
---
> [!quote] 1단계 문제 이해 및 설계 범위 확정
> **지원자**: 가장 중요하게 지원해야 할 기능들은 무엇인가요?
> **면접관**: 파일 업로드/다운로드, 파일 동기화, 그리고 알림(notification)입니다.
>
> **지원자**: 모바일 앱이나 웹 앱 가운데 하나만 지원하면 되나요, 아니면 둘 다 지원해야 합니까?
> **면접관**: 둘 다 지원해야 합니다.
>
> **지원자**: 파일을 암호화해야 할까요?
> **면접관**: 네.
>
> **지원자**: 파일 크기에 제한이 있습니까?
> **면접관**: 10GB 제한이 있습니다.
>
> **지원자**: 사용자는 얼마나 됩니까?
> **면접관**: 일간 능동 사용자(DAU) 기준으로 천만(10Million) 명입니다.

## 기능 요구사항
1. 파일 업로드: 드래그 앤 드롭으로 파일을 추가한다. 파일 하나는 최대 10GB.
2. 파일 다운로드
3. 여러 단말 동기화: 한 단말에서 파일을 추가하거나 고치면 다른 단말에도 자동으로 반영된다.
4. 파일 갱신 이력 조회 (revision history)
5. 파일 공유
6. 알림: 파일이 편집, 삭제, 공유되면 관련 사용자에게 알린다.
7. 지원 단말: 웹, 모바일 앱
8. 파일 암호화

제외: 구글 문서처럼 여러 사람이 한 문서를 동시에 편집하는 기능

## 비기능 요구사항
1. 안정성: 데이터를 절대 잃어버리면 안 된다.
	- 내구성. 서버나 데이터센터가 통째로 날아가도(DR) 복구할 수 있게 하라는 것
2. 빠른 동기화: 동기화가 느리면 사용자가 떠난다.
3. 네트워크 대역폭 절약: 모바일 데이터 요금제를 쓰는 사용자에게 특히 중요하다.
	- 파일을 통째로 주고받지 말라는 것. 
4. 규모 확장성: 트래픽이 아주 많아도 처리할 수 있어야 한다.
	- 서버만 늘리면 버티는 구조
5. 높은 가용성: 일부 서버가 죽거나 느려지거나 네트워크 일부가 끊겨도 계속 쓸 수 있어야 한다.
	- 서비스가 멈추지 않게 하라는 것. 한 대가 죽어도 다른 대가 이어받도록 모든 구성 요소를 이중화하고 장애 조치(failover)를 자동으로 한다.

## 규모
| 항목      | 값                                     |
| ------- | ------------------------------------- |
| 사용자     | 가입 5천만 명, DAU 천만 명                    |
| 저장 공간   | 사용자마다 10GB, 전체 최대 500PB               |
| 업로드     | 사용자마다 하루 2개, 평균 500KB                 |
| 업로드 QPS | 천만 x 2 / 86,400초 = 약 240, 최대 480      |
| 하루 유입량  | 천만 x 2 x 500KB = 10TB (1년이면 약 3.65PB) |

500PB는 모두가 10GB를 꽉 채웠을 때의 상한이다. 실제로 쌓이는 속도는 하루 10TB 정도다.

# 읽기 전의 개발
---
## 1단계: 업로드와 다운로드
---
로드밸런서 뒤에 API 서버 여러 대를 둔다. 파일은 S3에, 파일 정보(이름, 주인, S3 키)는 DB 한 대에 둔다. 파일은 요청 하나로 통째로 전송한다.

![[구글드라이브-1단계.svg]]

- 업로드: S3에 파일을 다 올린 다음 DB에 기록한다. 거꾸로 하면 없는 파일을 가리키는 행이 생길 수 있다.
- 다운로드: DB에서 S3 키를 찾아 S3에서 파일을 가져온다.
- S3를 쓴 이유: 서버마다 디스크를 두면 다른 서버에서는 그 파일을 찾을 수 없다. 디스크 하나만 두면 그 디스크가 죽을 때 파일을 전부 잃게 된다. S3는 주소는 하나인데 안에서 여러 데이터센터에 복제한다.

문제는 10GB 파일이다. LTE 10Mbps면 올리는 데 2시간 넘게 걸린다.

### 문제점
1. 끊기면 처음부터 다시 올린다.
2. 로드밸런서의 요청 크기 제한에 걸린다.
3. 업로드 하나가 서버 스레드를 몇 시간씩 점유한다.
4. 모든 바이트가 API 서버를 거친다.
5. S3는 PUT 한 번에 5GB까지만 허용한다.
6. DB가 SPOF라 죽으면 전체가 멈춘다. (나중 단계)

## 2단계: 8MB part로 나눠 올리기
---
1단계 문제점 1, 2, 3, 5번은 10GB를 요청 하나로 통째로 보내서 생긴다. 파일을 8MB part로 나눠 따로 올리고, 마지막에 S3가 합친다(S3 멀티파트 업로드).

![[구글드라이브-2단계.svg]]

- `POST /uploads` : 업로드를 시작한다. S3에서 업로드 id를 받고, DB에 업로드 진행 중으로 기록한다.
- `PUT /uploads/{id}/parts/{n}` : part 하나를 올린다. 어느 API 서버로 가도 된다.
- `GET /uploads/{id}` : 끊긴 뒤 받은 part 번호를 확인하고, 빠진 part만 다시 보낸다.
- `POST /uploads/{id}/complete` : S3가 part를 합치고, DB의 업로드 상태를 완료로 바꾼다.
- 다운로드는 HTTP Range 헤더로 구간을 나눠 요청한다.

8MB는 아래를 보고 정한다.
- S3 part 제약: 최소 5MB, 최대 10,000개
- 파일 최대 크기: 10GB
- 너무 작을 때: 요청 수가 많아져 왕복 시간, 인증 횟수, S3 요청 요금이 증가한다
- 너무 클 때: 느린 망에서 끊기면 다시 보내야 하는 양이 많고, 요청 하나가 오래 걸린다

### 문제점
1. 모든 바이트가 API 서버를 거친다. (1단계 4번)
2. 중간에 포기한 업로드의 part가 S3에 남아 비용이 나간다.
3. DB가 SPOF라 죽으면 전체가 멈춘다. (나중 단계)

## 3단계: S3와 직접 주고받기 (presigned URL)
---
2단계 문제점 1번은 파일 바이트가 API 서버를 거쳐서 생긴다. API 서버는 presigned URL만 발급하고, 파일 전송은 웹/앱과 S3 사이에서 직접 일어난다. presigned URL은 API 서버가 서명한 임시 URL이다. 정해진 시간 동안 그 part 하나만 올릴 수 있다.

![[구글드라이브-3단계.svg]]

업로드 흐름 (800MB 파일, part 8MB)
1. 웹/앱이 `POST /uploads`로 업로드를 시작한다. API 서버는 S3에서 uploadId를 받고, DB에 업로드 진행 중으로 기록한다.
2. API 서버가 part 100개의 presigned URL을 서명해서 돌려준다. URL 안에 uploadId와 part 번호가 들어 있다. 서명은 API 서버가 직접 계산하므로 S3 호출이 없다.
3. 웹/앱이 URL마다 part를 S3에 직접 PUT하고, 응답으로 받은 ETag를 모은다.
4. 웹/앱이 `POST /uploads/{id}/complete`를 보낸다. API 서버는 S3에 part 합치기를 요청하고, 크기를 확인한 뒤 DB의 업로드 상태를 완료로 바꾼다.

다운로드 흐름
1. 웹/앱이 `GET /files/{id}`로 다운로드용 presigned URL을 요청한다.
2. 웹/앱이 S3에 Range로 구간을 나눠 직접 요청한다.

- 끊긴 뒤에는 받은 part를 확인하고, 빠진 part의 URL을 다시 받아 올린다.
- URL은 만료 시간을 짧게 둔다(예: 15분). 새 나가면 만료 전까지 다른 사람도 올릴 수 있다. 10GB처럼 오래 걸리는 파일은 URL을 나눠서 발급한다.
- complete 때 S3의 실제 크기를 확인한다. 웹/앱이 알린 크기보다 크게 올릴 수 있다.

### 문제점
1. 중간에 포기한 업로드의 part가 S3에 남아 비용이 나간다. (2단계 2번)
2. DB가 SPOF라 죽으면 전체가 멈춘다. (나중 단계)

## 4단계: 변경 기록과 알림 서버 (long polling)
---
여러 단말 동기화를 다룬다. 폴링은 요청이 너무 많고 반영이 늦다. 그래서 바뀐 게 생기면 알림 서버가 알려 준다.

![[구글드라이브-4단계.svg]]

1. 폰이 알림 서버에 long polling으로 대기한다. 마지막으로 본 변경 번호(커서)를 같이 보낸다.
2. 노트북이 업로드를 끝내면 API 서버가 DB에 변경 기록을 쓰고 알림 서버에 알린다.
3. 알림 서버가 폰에 변경이 있다고 응답한다.
4. 폰이 API 서버에 커서 이후 변경 목록을 요청하고, 바뀐 파일을 S3에서 가져온다.

- 알림 서버는 API 서버와 따로 두고 논블로킹으로 구현한다. 연결을 오래 유지해도 스레드를 점유하지 않는다.
- 앱이 백그라운드에 있으면 FCM/APNs 푸시로 알린다.

> [!note]- 서버가 클라이언트에 먼저 보내는 방법
> | 방식 | 동작 | 서버가 보낼 수 있는 때 | 단점 |
> | --- | --- | --- | --- |
> | Polling | 정해진 간격마다 요청한다 | 요청이 왔을 때 | 바뀐 게 없어도 요청이 오고, 간격만큼 늦다 |
> | Long Polling | 서버가 변경이나 타임아웃까지 응답을 미룬다. 응답을 받으면 다시 요청한다 | 걸려 있는 요청이 있을 때 | 응답마다 다시 요청한다 |
> | SSE | 서버가 HTTP 응답을 닫지 않고 이벤트를 이어서 보낸다 | 아무 때나 (서버 → 클라이언트만) | HTTP/1.1이면 브라우저에서 도메인당 연결 6개 제한 |
> | WebSocket | HTTP 연결을 업그레이드한 뒤 양쪽이 메시지를 보낸다 | 아무 때나 (양방향) | HTTP 요청 단위가 아니라 로드밸런서, 배포 처리를 따로 챙겨야 한다 |
>
> - 동기/비동기는 방식이 아니라 서버 구현(블로킹/논블로킹)으로 갈린다.
> - Long Polling, SSE, WebSocket은 연결을 오래 유지한다. 동기 MVC(Tomcat 기본)는 요청 하나가 워커 스레드 하나를 응답까지 점유하고, 워커는 최대 200개다. 60초씩 기다리는 연결이 200개만 들어와도 다른 요청을 받지 못한다.
> - 앱이 백그라운드에 있으면 OS가 연결을 유지해 주지 않는다. 그래서 FCM/APNs 푸시를 쓴다.
> - 4단계는 Long Polling을 골랐다. 변경이 드물고 양방향이 필요 없다.
>
> Spring에서는 아래 셋 중 하나로 만든다.
>
> | 방법 | 기다리는 동안 | 특징 |
> | --- | --- | --- |
> | MVC + DeferredResult | 워커를 풀에 돌려준다 | 기다리는 부분만 바꾸고 나머지는 보통 MVC 코드다. SSE는 SseEmitter |
> | MVC + 가상 스레드 | OS 스레드를 반납한다 | 코드를 바꾸지 않고 JPA도 그대로 쓴다. Java 21 이상, 24 미만은 synchronized 안에서 기다리면 OS 스레드를 점유한다 |
> | WebFlux + Netty | 콜백 객체만 유지한다 | 연결당 메모리가 가장 작다. 코드 전체를 Mono/Flux로 쓰고, JPA 대신 R2DBC를 쓴다 |
>
> MVC 두 방법은 Tomcat 연결 상한(maxConnections, 기본 8192)을 올려야 한다.

API 서버는 A의 연결이 어느 알림 서버에 있는지 모른다. 그래서 Redis Pub/Sub에 사용자별 채널을 둔다. A의 대기 요청을 가진 알림 서버가 `user:A` 채널을 구독하고, API 서버는 이 채널에 발행한다. Redis는 구독한 서버에만 전달한다. 메시지를 놓쳐도 다음 long polling 때 커서로 알아챈다.

![[구글드라이브-4단계-알림전달.svg]]

### 문제점
1. 두 단말이 같은 파일을 각자 고치면 이전에 올렸던 수정본이 덮어써진다.
2. 한 글자만 고쳐도 파일 전체를 다시 올리고 다시 받아야 한다.
3. long polling은 최대 60초마다 다시 연결하고, 그때 서버가 바뀔 수 있다. 그래서 채널 구독과 해제가 계속 일어나고, 연결 200만 개 기준으로 초당 약 3.3만 번 발생한다.
4. 포기한 업로드의 part가 S3에 쌓여 비용이 나간다. DB와 Redis가 SPOF다. (나중 단계)

## 5단계: 충돌 처리, 갱신 이력, 버킷 채널
---
4단계 문제점 1번(동시 수정)과 3번(구독 변경)을 고친다.

### 충돌과 갱신 이력
파일을 덮어쓰지 않고 버전마다 행(S3 키, 올린 기기, 시각)을 추가한다. S3 키는 업로드마다 새로 생성한다.

![[구글드라이브-5단계-충돌.svg]]

1. 노트북이 편집을 시작하면 Redis에 `editing:파일id`를 TTL 60초로 기록하고, 편집하는 동안 갱신한다.
2. 같은 파일을 연 폰에는 알림 채널로 편집 중이라고 보낸다. 폰은 편집 대기를 표시하고, 저장이 끝나면 최신본을 받아 편집한다.
3. 오프라인 편집처럼 그래도 겹치면, complete에 보낸 기준 버전이 현재 버전과 달라 충돌로 판단한다. 폰의 수정본은 충돌 사본으로 저장하고, 최신 받기와 나란히 비교 중에서 고르게 한다.

- 되돌리기는 옛 버전의 S3 키를 가리키는 새 버전을 추가한다. 어느 쪽을 골라도 수정본을 잃지 않는다.

### 구독 변경: 버킷 채널
사용자를 `hash(userId) % 1024`로 버킷에 나누고 채널도 버킷 단위(`bucket:517`)로 둔다. 로드밸런서는 버킷 번호로 안정 해시를 계산해 같은 버킷 사용자를 같은 알림 서버로 보낸다.

![[구글드라이브-5단계-버킷.svg]]

- 알림 서버는 들어온 사용자의 버킷을 구독하고, 2분 동안 비면 해제한다. 구독은 서버를 추가하거나 뺄 때만 바뀐다.
- API 서버는 A의 버킷 채널에 발행한다. 서버가 죽어서 놓친 변경은 커서로 알아챈다.

### 문제점
1. 한 글자만 고쳐도 파일 전체를 다시 올리고 다시 받아야 한다. 버전마다 파일 전체가 저장된다.
2. 포기한 업로드의 part가 S3에 쌓여 비용이 나간다. DB와 Redis가 SPOF다. (나중 단계)

## 6단계: 블록 단위 저장
---
5단계 문제점 1번은 파일을 통째로 저장해서 생긴다. 파일을 평균 8MB 블록으로 나눠 블록마다 S3 객체를 하나씩 두고, 버전은 블록 해시 목록으로 저장한다.

![[구글드라이브-6단계.svg]]

1. 단말이 파일을 블록으로 나누고, 블록마다 SHA-256 해시를 계산한다.
2. 해시 목록을 보내면 API 서버가 DB에 없는 해시만 골라 presigned URL을 발급한다.
3. 단말은 없는 블록만 `blocks/{hash}`로 S3에 올린다.
4. complete 때 버전 행에 해시 목록을 저장한다. 기준 버전 비교는 5단계와 같다.

- 다른 단말은 새 버전의 해시 목록을 보고, 자기에게 없는 블록만 S3에서 가져온다.
- 블록 하나는 PUT 한 번으로 올라가서 멀티파트 업로드는 더 이상 쓰지 않는다.

### 블록 경계: 내용 기반 분할
8MB 위치마다 자르면 파일 앞에 1바이트만 끼워 넣어도 뒤쪽이 전부 밀려서 모든 블록 해시가 바뀐다. 그래서 위치가 아니라 내용을 보고 자른다. 48바이트 창을 밀면서 rolling hash를 계산하고, 하위 23비트가 0인 곳에서 자른다. 블록 크기는 평균 8MB로 두고, 최소 2MB와 최대 32MB로 제한한다. 경계가 내용으로 정해지므로 끼워 넣은 곳의 블록 하나만 바뀐다.

### 안 쓰는 블록 정리: 참조 수
블록은 여러 버전이 나눠 쓰고, 업로드를 포기하면 어느 버전에도 속하지 않은 블록이 생긴다. 그래서 DB에 블록마다 참조 수를 둔다.
- URL을 발급할 때 블록 행을 참조 수 0으로 추가하고, complete 때 1씩 올린다. 버전이 보관 기간을 넘겨 지워지면 1씩 내린다.
- 배치 작업이 참조 수가 0이고 24시간 넘게 쓰이지 않은 블록을 지운다. 이미 있는 블록이라고 답할 때도 사용 시각을 갱신해서, 업로드 중에 지워지지 않게 한다.
