01무엇을 만드나

책 277~280쪽

동기화 폴더

구글 드라이브에서 중요한 기능은 업로드 자체보다 동기화다. 데스크톱 앱을 깔면 컴퓨터에 드라이브 폴더가 생기는데, 이 폴더는 클라우드에 있는 원본을 그대로 따라간다. 노트북에서 파일을 고치면 원본이 바뀌고, 휴대폰과 웹에서도 바뀐 파일이 보인다.

보충그래서 이 장에서 말하는 "다운로드"는 브라우저에서 받는 사본이 아니라, 동기화 폴더를 원본에 맞추는 일이다. 브라우저로 받은 파일은 독립된 사본이라 원본이 바뀌어도 그대로다. 반면 동기화 폴더의 파일은 남이 고치면 따라 바뀌는데, 버그가 아니라 이 기능이 원래 하는 일이다. 파일을 고칠 수 있는 사람은 내가 편집 권한을 준 사람뿐이고, 내가 아직 올리지 않은 수정은 덮어쓰지 않는다(9절).

02서버 한 대에서 출발

책 280~285쪽

처음에는 서버 한 대에 웹 서버(아파치), 데이터베이스(MySQL), 파일을 저장할 1TB 디스크를 모두 둔다. 사용자마다 디렉터리를 하나씩 주고, 올린 파일을 그대로 저장한다. 업로드, 다운로드, 갱신 이력 조회 API 세 개면 기능은 돌아간다.

책은 먼저 user_id로 샤딩해 파일을 여러 서버에 나누지만, 서버가 죽으면 파일을 잃는다는 걱정이 남는다. 그래서 파일은 아마존 S3에 맡긴다. S3는 데이터를 여러 지역(region)에 복제할 수 있어서, 한 지역 전체가 멈춰도 파일이 남는다. 이어서 남은 서버도 역할별로 나눈다.

구성 요소하는 일
로드밸런서요청을 여러 API 서버에 나누고, 죽은 서버는 피해 간다.
API 서버인증, 메타데이터 갱신 등 파일 업로드를 뺀 거의 모든 일을 맡는다. 상태가 없어 필요한 만큼 늘릴 수 있다.
메타데이터 DB사용자, 파일, 버전 정보를 둔다. 파일 저장 서버에서 떼어 내 복제하고 샤딩한다.
S3파일 내용을 둔다. 두 개 이상의 지역에 복제한다.

03파일 정보와 내용을 나눈다

책 287~291쪽 내용을 묶음 보충

2절에서 DB와 S3를 나눈 것이 이 설계의 뼈대다. 파일 하나는 두 군데에 나뉘어 저장된다. 이름과 버전 같은 정보는 메타데이터 DB에, 실제 내용은 블록으로 잘라 S3에 둔다.

구분메타데이터 DBS3
담는 것이름, 경로, 최신 버전, 블록 목록파일 내용(블록)
크기파일마다 수백 바이트파일 크기만큼
바뀌는 방식파일을 고칠 때마다 갱신한 번 쓰면 바뀌지 않음

이렇게 나누면 "파일이 바뀌었다"는 사건이 메타데이터 한 줄을 고치는 일로 줄어든다. 책이 메타데이터 DB로 ACID를 지원하는 관계형 DB를 고른 것도 이 한 줄을 정확하게 지켜야 하기 때문이다. 캐시를 둘 때는 DB를 먼저 갱신하고 캐시 항목을 지워서, 캐시가 옛 버전을 들고 있지 않게 한다.

04파일을 블록으로 쪼갠다

책 287~289쪽

10GB 파일을 한 번에 올리다 끊기면 처음부터 다시 올려야 하고, 한 글자만 고쳐도 10GB를 다시 보내야 한다. 그래서 파일을 4MB 블록으로 자른다. 드롭박스와 같은 크기다.

  • 블록마다 SHA-256 해시를 계산한다. 내용이 같으면 해시가 같고, 1비트만 달라도 해시가 완전히 달라진다.
  • 블록은 해시를 이름으로 삼아 S3에 저장한다. 내용이 곧 주소다.
  • 파일의 한 버전은 해시를 순서대로 늘어놓은 블록 목록이 된다. 메타데이터 DB에는 이 목록만 저장한다.
  • 블록 단위로 올리면 이어 올리기가 저절로 된다. 끊겼다가 다시 연결되면 아직 안 올라간 블록만 올리면 된다.
보충책의 "블록 저장소 서버"는 AWS EBS 같은 블록 스토리지가 아니다. 파일을 블록 단위로 처리하는 업로드/다운로드 서버이고, 실제 저장은 S3가 한다.

05수정하면 바뀐 블록만 보낸다

책 289~290쪽 (델타 동기화)

책은 "수정된 블록만 동기화한다"고만 설명하고, 어느 블록이 바뀌었는지 알아내는 방법은 말하지 않는다. 방법은 블록 목록 두 개를 비교하는 것이다.

  1. 클라이언트가 고친 파일을 다시 자르고 해시를 계산해 v2 목록을 만든다.
  2. v1 목록과 비교하면 두 번째 해시만 다르다. d48b 블록 하나(4MB)만 올린다. 14MB 파일을 고쳤는데 전송량은 4MB다.
  3. 메타데이터 DB에 v2 목록을 기록한다.

S3에서 덮어쓰는 블록은 없다. 7c0e는 v1 목록이 계속 가리키므로 남는다. 덕분에 갱신 이력이 덤으로 생긴다. v1으로 되돌리려면 최신 버전이 v1 목록을 가리키게 바꾸면 된다.

보충파일은 클라이언트가 쪼개야 한다

책의 설계에서는 블록 저장소 서버가 파일을 쪼갠다. 그러면 클라이언트는 파일 전체를 블록 저장소 서버로 보내야 하고, 바뀐 블록만 보내는 구간은 데이터센터 안쪽뿐이다. 1절에서 아끼려던 것은 사용자의 모바일 데이터였는데, 정작 그 구간으로는 14MB가 그대로 나간다.

사용자 회선을 아끼려면 클라이언트가 파일을 쪼개고 해시를 계산한 뒤, 서버에 없는 블록만 올려야 한다. 드롭박스 데스크톱 앱도 이렇게 한다. 쪼개기와 해시 계산은 가벼워서 플랫폼마다 구현해도 부담이 작다. 압축과 암호화는 서버에 남겨 둔다.

보충고정 크기 블록의 약점

4MB 경계는 파일 시작에서 4MB, 8MB, 12MB처럼 위치로 정해진다. 내용을 제자리에서 고치면 문제없지만, 맨 앞에 한 글자를 끼워 넣으면 뒤쪽 내용이 전부 한 칸씩 밀려 모든 블록의 해시가 바뀐다. 아래는 4글자를 블록 크기로 삼아 단순화한 예시다. 고정 크기 방식은 4글자마다 자르고, 내용 기준 방식은 마침표 뒤에서 자른다.

내용 기반 청킹(CDC, content-defined chunking)은 위치 대신 내용을 보고 경계를 정한다. 실제로는 작은 창을 한 바이트씩 밀며 롤링 해시를 계산하고, 해시값이 정해 둔 조건을 만족하는 지점에서 자른다. 끼워 넣은 곳 근처의 블록만 바뀌고 뒤쪽 경계는 그대로 남는다. restic, borg 같은 백업 도구가 이 방식을 쓴다.

사진이나 영상처럼 고칠 때마다 파일 전체가 새로 만들어지는 경우는 어느 방식을 써도 이득이 작다. 책의 설계와 드롭박스는 고정 크기 블록을 쓴다.

06업로드 전체 흐름

책 289쪽, 292~293쪽

4절과 5절을 합치면 업로드는 "블록 목록부터 커밋해 보고, 서버에 없는 블록만 올린다"는 흐름이 된다. 드롭박스가 기술 블로그에서 소개한 동기화 방식과 같다.

얻는 것이 흐름에서 처리되는 방식
델타 동기화서버에 없는 블록만 올린다.
중복 제거이미 있는 블록이면 서버가 요청하지 않는다. 같은 파일을 다른 폴더에 복사하면 블록을 하나도 올리지 않는다.
이어 올리기끊겨도 다시 커밋하면 서버가 아직 없는 블록만 다시 요청한다.
충돌 감지커밋할 때 기준 버전을 비교한다(9절).
완전한 버전만 공개블록이 다 올라간 뒤에 새 버전을 커밋하므로, 다른 단말이 반쯤 올라간 파일을 받을 일이 없다.

블록 저장소 서버는 받은 블록을 압축한 다음 암호화해서 S3에 넣는다.

순서는 압축이 먼저다. 암호화된 데이터는 무작위 바이트처럼 보여서 압축되지 않는다. 이미 압축된 형식은 다시 압축해도 거의 줄지 않으므로 건너뛴다.

책은 업로드 순서가 다르다. 메타데이터를 먼저 "대기 중"으로 기록하고 파일을 올린 뒤, S3의 완료 콜백을 받아 "완료"로 바꾼다. 위 흐름은 블록이 다 올라간 뒤 한 번에 커밋하므로 대기 상태와 콜백이 필요 없다.

07다른 단말이 알아채기

책 295~296쪽

노트북에서 커밋이 끝나면 휴대폰에 그 사실을 알려야 한다. 서버가 클라이언트에 먼저 알리는 방법으로 책은 롱 폴링과 웹소켓을 비교한 뒤 롱 폴링을 고른다. 알림은 서버에서 클라이언트로 가는 한 방향이고, 자주 생기지 않으며, 양도 적기 때문이다. 웹소켓은 채팅처럼 양방향으로 자주 주고받는 서비스에 맞다. 드롭박스도 롱 폴링을 쓴다.

  • 클라이언트가 요청을 보내면 서버는 변경이 생기거나 타임아웃이 될 때까지 응답을 미룬다. 응답을 받으면 클라이언트는 곧바로 다시 요청한다.
  • 알림에는 "바뀐 게 있다"는 신호만 담는다. 무엇이 바뀌었는지는 API 서버에서 따로 받는다.

보충꺼져 있던 단말은 커서로 따라잡는다

책은 접속하지 않은 단말의 변경 정보를 "오프라인 사용자 백업 큐"에 쌓아 둔다고 한다. 이러면 단말마다 큐가 하나씩 필요하고, 오래 꺼져 있던 단말의 큐는 끝없이 쌓인다. 실제 서비스에서는 보통 변경 기록과 커서를 쓴다. 폴더마다 변경 기록에 순번을 붙여 남기고, 단말은 마지막으로 반영한 순번 하나만 기억한다.

  • 휴대폰은 다시 켜지면 "41 이후 변경분"을 한 번 요청해 42, 43을 받는다.
  • 알림을 놓쳐도 잃는 변경이 없다. 다음에 커서로 물어보면 빠진 변경이 모두 나온다. 알림 서버가 죽어도 데이터는 안전하다.
  • 변경 기록을 메타데이터 DB에 두면 파일 정보 변경과 같은 트랜잭션으로 묶을 수 있다.

08내려받아 다시 조립하기

책 294~295쪽

받는 쪽도 블록 목록을 비교한다. 새 목록에는 있는데 내 단말에 없는 블록만 내려받는다.

책이 말하는 "파일 재구성"은 블록을 제자리에 끼워 넣는 일이 아니다. 내 단말에 있는 블록과 새로 받은 블록을 목록 순서대로 이어 붙여 파일을 새로 만들고, 임시 파일에 다 쓴 뒤 원래 파일과 이름을 바꾼다. 중간에 끊겨도 원래 파일은 그대로다.

받는 도중에 누가 v3을 올려도 v2와 v3이 섞이지 않는다. v2 목록이 가리키는 블록은 바뀌지 않기 때문이다. v2를 다 받은 뒤 v3 알림을 받아 한 번 더 동기화한다.

09동시에 고치면

책 286쪽

두 사람이 같은 파일을 동시에 고치면, 책은 먼저 처리된 쪽이 이기고 나중 쪽은 충돌로 처리한다고만 한다. 보충 판단 기준은 도착 시각이 아니라 어느 버전을 고쳤는지다. 클라이언트는 커밋할 때 자기가 고친 기준 버전을 함께 보내고, 서버는 그 버전이 지금도 최신일 때만 갱신한다.

UPDATE file
   SET latest_version = 5
 WHERE id = 42
   AND latest_version = 4;   -- 클라이언트가 보낸 기준 버전
-- 갱신된 행이 0개면 누군가 먼저 v5를 만든 것이므로 충돌

충돌 난 쪽은 자기 수정본을 별도 파일로 남기고, 원래 파일은 최신 버전으로 맞춘다. 두 내용이 모두 남고, 합치는 일은 사용자가 한다.

남이 고친 v5가 도착했을 때 내 단말에 아직 올리지 않은 수정이 있으면 같은 방식으로 처리한다. 내 파일의 기준 버전(v4)이 서버 최신(v5)과 다르므로 충돌이고, 내 수정은 덮어쓰지 않고 충돌 사본으로 남긴다.

사진이나 엑셀 같은 바이너리 파일에는 일반적인 병합 규칙이 없어서 자동으로 합치지 않는다. 구글 문서처럼 동시 편집이 되는 서비스는 OT나 CRDT 같은 별도 기법을 쓰며, 이 장의 범위가 아니다.

10데이터 모델

책 291~292쪽

지금까지 나온 정보를 테이블로 옮기면 다음과 같다. 초록색 테이블은 책 스키마에 없던 것이다.

테이블담는 것
user, device사용자와 단말. 한 사용자가 단말을 여러 대 쓴다. push_id는 모바일 푸시 알림용이다.
namespace사용자의 루트 폴더. 공유 폴더도 namespace로 표현한다.

file_version버전마다 한 줄. 읽기 전용이라 이력이 훼손되지 않는다.
file_version_block버전 하나가 어떤 블록을 어떤 순서로 쓰는지
block블록 내용 하나에 한 줄. 해시가 키다.
journal7절의 변경 기록
보충책 스키마(그림 15-13)의 block 테이블에는 해시 컬럼이 없고, 블록 행 하나가 버전 하나에 묶여 있다. 이러면 v1과 v2가 같은 블록을 함께 쓰는 모습을 나타낼 수 없다. 그래서 블록 내용(block)과 버전별 블록 순서(file_version_block)를 나눴다. 본문에 나오는 device의 push_id와 업로드 상태(status)도 책의 그림에는 빠져 있다.

11저장 공간과 장애

책 296~298쪽

저장 공간 줄이기

방법내용
중복 제거같은 해시의 블록은 한 번만 저장한다. 복사본과 이전 버전이 같은 블록을 가리킨다.
버전 정리보관할 버전 수에 상한을 두고, 자주 바뀌는 파일은 중요한 버전만 남긴다.
콜드 스토리지몇 달 넘게 쓰지 않은 블록은 S3 글래시어처럼 싼 저장소로 옮긴다. 대신 꺼낼 때 시간이나 비용이 더 든다.
보충책은 중복 제거를 계정 단위로 한다. 모든 사용자를 통틀어 제거하면, 업로드가 순식간에 끝나는 것만 보고 다른 사람이 같은 파일을 가졌는지 알아낼 수 있다. 2011년 드롭박스에서는 해시만으로 남의 파일을 가져오는 도구(Dropship)가 공개되기도 했다. 또 버전이 지워져도 블록은 바로 지우지 않는다. 아무 버전도 가리키지 않는 블록만 나중에 지운다.

장애 대응

장애대응
로드밸런서부 로드밸런서가 이어받는다. 둘은 박동(heartbeat) 신호로 서로 상태를 확인한다.
API 서버상태가 없으므로 로드밸런서가 죽은 서버로 요청을 보내지 않으면 된다.
블록 저장소 서버다른 서버가 끝내지 못한 작업을 이어받는다.
S3다른 지역의 복제본에서 가져온다.
메타데이터 캐시복제해 두고, 죽은 노드는 새것으로 바꾼다.
메타데이터 DB주 서버가 죽으면 부 서버 하나를 주 서버로 올린다. 부 서버가 죽으면 다른 부 서버가 읽기를 맡는다.
알림 서비스서버 한 대가 롱 폴링 연결을 100만 개 넘게 들고 있다. 한 대가 죽으면 100만 명이 한꺼번에 재접속해야 해서 복구가 느리다. 재접속 전에 무작위로 조금 기다리게 하면 몰림이 줄고, 커서 방식이라 늦게 붙어도 잃는 변경은 없다.

12한 장으로 정리

책 298~299쪽

면접에서 설명할 결정

  1. 메타데이터와 파일 내용을 나누고, 강한 일관성은 메타데이터에만 건다.
  2. 파일을 4MB 블록으로 쪼개고 해시를 이름으로 저장한다. 델타 동기화, 중복 제거, 이어 올리기, 갱신 이력이 모두 여기서 나온다.
  3. 업로드는 블록 목록 커밋 → 없는 블록 업로드 → 다시 커밋 순서로 한다. 커밋할 때 기준 버전을 비교해 충돌을 잡는다.
  4. 알림은 롱 폴링으로 "바뀐 게 있다"만 알리고, 변경 내역은 커서로 가져간다.

다른 선택지

선택지내용
클라이언트가 S3에 직접 업로드API 서버가 미리 서명된 URL(presigned URL)을 주면 클라이언트가 S3로 바로 올린다. 서버를 거치지 않아 빠르다. 책은 분할, 압축, 암호화를 플랫폼마다 구현해야 하고 클라이언트 쪽 암호화가 위험하다는 점을 단점으로 든다. 보충 분할은 5절처럼 어차피 클라이언트가 해야 하고, 암호화는 HTTPS와 S3 서버 측 암호화로 대신할 수 있다. 남는 단점은 서버가 업로드 내용을 중간에서 검사하거나 압축하기 어렵다는 점이다.
접속 상태 관리 분리단말의 접속 상태를 관리하는 로직을 알림 서비스에서 떼어 별도 서비스로 만들면 다른 서비스도 함께 쓸 수 있다.
