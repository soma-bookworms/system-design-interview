# 발표 자료 작성 가이드

## 개요

URL 단축키를 설계해보자

## 본문

### 단축 URL 시스템 통신 절차
1. 원래 URL을 단축 URL로 변환해주는 엔드포인트
2. 단축 URL로 tinyurl 서버 요청
3. status 301로 Location에 원래 URL을 담아줌
4. 원래 URL 방문

### 301과 302 응답의 차이
- 301 Permanently Moved
    - 해당 URL에 대한 HTTP 처리 책임이 영구적으로 Location 헤더에 반환된 URL로 이전되었다는 응답
    - 영구적으로 이전되었기에 브라우저가 이 응답을 Cache한다.
    - 따라서 추후 같은 단축 URL에 요청을 보내야할 때, 캐시된 원래 URL로 요청을 보낸다.
- 302 Found
    - 주어진 URL로의 요청이 일시적으로 Location 헤더가 지정하는 URL에 의해 처리되어야 한다는 응답
    - 따라서 클라이언트의 요청은 언제나 단축 URL 서버에 먼저 보내진 후 원래 URL로 리다이렉션 당해야한다.
- 서버 부하를 줄일 땐 301이 좋지만 트래픽 분석에서는 302가 유리하다.

### URL 단축
- 결국 중요한 것은 긴 URL을 해시 값으로 대응 시킬 수 있는 해시 함수 fx를 찾는 일
- 이 해시 함수는 주어지는 긴 URL 마다 서로 다른 해시 값을 뱉어야 하며, 반대 복원도 지원해야 한다.
- 사용가능한 문자 종류는 10+26+26=62종, 62^7 ~= 3.5조의 URL이 표현 가능하기에, 7자리면 목적을 달성 가능하다
- 62진법으로 변환하면 62종 문자로 7자의 단축 URL을 반환할 수 있다.

## 설계

> "문제 이해 및 설계 범위 확정" 부분만 읽고 선행적으로 설계를 진행하고, 해당 장을 전부 읽은 후에 문제 해결에 대한 이상적인 방법을 정리한다.

### 요구사항

1. URL 단축: 주어진 긴 URL을 훨씬 짧게 줄인다
  - 숫자 0-9, 영소문자 a-z, 영대문자 A-Z 만 사용 가능
2. URL 리디렉션: 축약된 URL로 HTTP 요청이 오면 원래 URL로 안내
3. 높은 가용성과 규모 확장성, 장애 감내가 요구됨

### 개략적 추정
- 매일 1억 개의 단축 URL 생성
- 초당 쓰기 연산: 1억/24/3600 = 1160
- 읽기 연산과 쓰기 연산 비율이 10:1이라고 하면 읽기 연산은 초당 11600회
- URL 단축 서비스를 10년간 운영한다고 가정하면 1억*365*10 = 3650억개의 레코드
- 축약 전 URL의 평균 길이는 100
- 따라서 10년 동안 필요한 저장 용량은 3650억*100바이트 = 36.5TB

### 1단계(문제 정의)만 읽은 후 설계

- 인코딩이나 해싱으로 변환하여 저장은 할텐데, 역방향 추적은 어떻게 하는가?
- 결국 특정 URL에 대응하는 단축 URL을 생성하여 K-V 구조로 저장하는 형태 아닐까?

### 해당 장을 전부 읽은 후 설계

1. 입력으로 긴 URL을 받고
2. DB에 해당 URL이 있는지 검사하고 -> 있으면 이미 존재하는 URL이니 반환하고
3. DB에 없는 경우 해시 함수로 Unique ID를 생성하고 62진법을 통해 ID를 단축 URL로 만들고
4. ID, 단축 URL, 원본 URL을 DB 레코드로 저장한다.
