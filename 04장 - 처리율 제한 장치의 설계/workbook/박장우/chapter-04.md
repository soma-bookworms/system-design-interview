
# 구현 요구사항
---
1. 설정된 처리율을 초과하는 요청은 정확하게 제한한다.
	- "정확하게" 라는 말이 Race Condition Issue 에 대한 부분을 잘 처리해야함을 내포하는 것 같음

2. Rate Limiter는 HTTP 응답시간에 나쁜 영향을 주어서는 곤란하다.
 	- 미들웨어에서 시간이 오래걸리는건 전체적인 영향을 줄 수 있다. In-Memory DB 를 사용해야함

 3. 가능한 적은 메모리를 사용한다.
 	- 필요한 정보만 In-Memory DB에 저장해야함. 

 4. 분산형 처리율 제한 : 하나의 처리율 제한 장치를 여러 서버나 프로세스에서 공유할 수 있어야한다.
 	- CAP 조건 세 가지 중 Consistency에 대한 것을 이야기한다. **이걸 잘 하는게 가장 어려울듯.**
 	- 해당 장에서는 어떻게 해야되는지에 대해 크게 설명해주진 않는다. **별도로 공부 많이 해야하는 지점**

 5. 요청이 제한되었을 때는 그 사실을 사용자에게 분명하게 보여줘야 한다.
 	- 걍 429에러 잘 터트리라는듯.

 6. 높은 내결함성 : 제한장치에 장애가 생기더라도 전체 시스템에 영향을 주어서는 안된다.
 	- Rate Limiter에 문제가 생겨도 서비스로 자연스럽게 흘러가도록 폴백 로직을 잘 구현해야한다.

### Rate Limiter 구현하는 위치
책에서는 클라이언트가 아닌 서버 혹은 미들웨어에 Rate Limiter를 두라고한다. 당연한소리.
1. API 엔드포인트가 노출되면 그냥 파이썬 스크립트나 curl로 폭탄을 투하할 수 있다.
2. 웹사이트의 JS는 그냥 개발자 도구에서 고칠 수 있고, 앱도 리패키징이 가능하다.
3. 사용자의 IP, ID가 아닌 각 플랫폼에서 독자적으로 카운트를 센다. 즉, 웹앱이라면, 동시에 여러 곳에서 요청을 보내도 알 수 있는 방법이 없다.
4. 등등등.....

이런 문제는 단순히 Rate Limiter에만 적용되는 이야기는 아니다.
반드시 개발 할 때 클라이언트는 얼마든지 조작 가능하다는 것을 인지하고 개발해야한다.

### Rate Limit 알고리즘
#### 토큰 버킷 token bucket

매우 간단하다. 
1. 특정 시간마다 버킷에 토큰이 가득 채워지고
2. 사용자 요청이 들어오면 토큰을 하나 소모한다.
3. 토큰이 없으면 429 
4. 토큰을 가지는 한도는 버킷의 용량만큼이 최대.

두 가지 parameter가 필요하다.
- 버킷크기
- 토큰을 몇초(몇분)에 얼만큼 공급할지

장점은
- 구현이 쉽다.
- 메모리 사용 측면에서 효율적이다.
- 짧은 시간에 검증되는 트래픽도 처리 가능하다. 
단점은
- 버킷 크기와 토큰 공급률 두가지 인자를 서비스에 맞게 적절히 튜닝하는 지점을 찾기 어렵다.

<br>

#### 누출 버킷 leaky bucket

1. 요청이 들어오면 큐를 보고
2. 큐가 가득 차있으면 요청을 버리고
3. 큐가 비어있으면 요청을 그대로 받는다.

두 가지 parameter가 필요하다.
- 큐의 크기
- 처리율 (실제 처리율이 아닌 시간당 몇개의 요청을 큐에서 빼낼지 결정하는 parameter)

처리율은 사용자가 지정하는 값이다. 
즉, 실제 작업의 처리속도와는 아무런 관련이 없다. 

다만, 실제 작업의 처리속도보다 이 처리율이 짧으면 Rate Limit을 거는 의미가 없어지겠지..

토큰 버킷과의 차이점은 **일정 시간에 들어오는 양, 나가는 양이 일정하다는 것.** 
토큰 버킷은 버킷이 채워졌을 때 한번에 버스트가 가능함. 


<br>

#### 고정 윈도 카운터 fixed window counter

윈도우 개념이 나오는데 중요함. 
Rate Limit 이외에도 DE 건드릴 때도 많이 나옴.
- Fixed Window : 범위로 자르고 Window는 움직이지 않음.
	![](asset/Pasted%20image%2020260828024319.png)
- Sliding Window : 현재 보고있는 Window가 조금씩 움직임.
	![](asset/Pasted%20image%2020260828024339.png)


고정 윈도우 카운터는 타임라인을 일정한 간격으로 전부 자르고 (윈도우) 그 안에서 정해진 만큼의 양만 요청을 처리할 수 있다.
1. 요청이 들어오면 현재 타임라인을 확인.
2. 현재 타임라인에서 처리한 요청수가 최대 버스트 수를 넘어가면 요청을 버리고
3. 아니면 요청을 처리.

타임라인 직전에 요청을 막 보내고, 타임라인 끝나고 요청을 막 보내면 해당 1분(예시)을 봤을 때는 내가 설정한 최대 처리량보다 더 많은 요청을 처리한다.

고정 윈도우 카운트의 인자는
- 윈도우를 얼만큼의 시간 단위로 쪼갤지  
- 한 윈도우에 얼만큼의 요청을 처리할지

**언뜻 보기에는 토큰버킷과 차이점이 없어보인다.** 실제로도 별로 차이는 없다.
- 윈도우를 얼만큼의 시간 단위로 쪼갤지  (= 토큰을 얼만큼의 시간 간격으로 공급할지)
- 한 윈도우에 얼만큼의 요청을 처리할지 (= 시간마다 얼만큼의 토큰을 공급할지)

다만 토큰 버킷은 버스트의 크기를 한 번 더 조절할 수 있다. **공급하는 양과 버킷의 총 크기를 조절이 가능**하다. 고정 윈도우는 불가능하다.

<br>

#### 이동 윈도 로깅 sliding window logging

굉장히 수상한 알고리즘이다.

위와 다르게 Fixed가 아닌 Sliding을 사용한다.

1. 들어오는 모든 요청의 타임라인을 로그에 기록한다.
2. 현재 시간보다 정한 시간(예, 1분)보다 이전의 로그들은 전부 지우고 로그 개수를 확인한다.
3. 로그 개수가 내가 정한 최대보다 크면 요청을 버린다.
4. 작으면 요청을 처리한다.

문제는 로그에 기록하고 버릴지 말지를 정한다는 것. 
	즉, 버린 요청 때문에 실제 요청 처리는 안 되고 있는데 요청이 와도 버리게 되는 상황이 발생할 수 있다.

TCP에서 의미없는 연결로 소켓을 차지하는 것 처럼 이것도 실제 사용자는 올바른 사용을 못하는 혹은 계속 요청을 보내면 무한히 사용을 못하는 문제가 발생 할 수 있다.

해결방법은 그냥 실패 로그는 기록을 안 하면된다.
- 심지어 고정 윈도우 카운트의 단점도 해결할 수 있다.
- 실패를 기록하지 않으면, 타임라인 어디를 봐도 내가 정한 1분간 처리율을 넘지 못한다.


루아스크립트로 충분히 가능하다.
- sorted set을 사용할 때, score는 타임스탬프, value는 member의 고유값이다.
- 그냥 현재 타임스탬프에 내가 설정한 윈도우 크기만큼 빼서 그것보다 작은 것은 계속 지우고
- 개수 확인한 뒤에 남아있으면 요청을 처리, 불가능하면 버리면 된다.

<br>

#### 이동 윈도 카운터 sliding window counter

고정 윈도 카운터와 이동 윈도 로그를 절충한 버전.

1. 타임라인은 전부 쪼개져있다.
2. 이동 윈도우는 이동하면서 걸쳐져 있는 윈도우를 확인
3. 이전 윈도우와 현재 윈도우 각각 몇퍼센트씩 걸쳐져 있는지를 확인하고
4. 그에 맞춰 현재 카운터를 제공한다.

고정 윈도 카운터의 단점(초기화 직전에 요청이 몰리면 문제 발생할 가능성이 있다)을 절충한다.

카운터 = 현재 윈도우 카운터 + 과거 윈도우 카운터 x 과거 윈도우에 걸쳐져 있는 퍼센트

타임라인이 쪼개져있더라도 그 안에서 슬라이딩 윈도우가 움직이면서 이전 타임라인의 요청 개수도 고려하며 처리량을 제한한다.

# 분산 시스템에서의 Rate Limiter
---
## Race Condition
![](asset/Pasted%20image%2020260828131452.png)
두 스레드에서 읽고 쓰는 작업이 완전히 동시에 일어나면 문제가 발생한다.

#### atomic commands

Redis에는 기본적으로 여러가지 원자적 명령어를 제공한다.

INCR, DECR, GETSET, SETNX, SADD 등등...

#### lua script

루아스크립트를 이용하면 여러가지 Redis 명령어를 원자적으로 묶을 수 있다.

트랜잭션이 없는 Redis에서 트랜잭션처럼 쓸 수 있다. 

#### 비관락

안 쓰는게 맞다. Rate Limiter 때문에 오히려 명령어들은 락을 획득하려고 직렬화되고, 락 획득 연산이 추가된다. 락 획득을 위해 여러 번의 네트워크 왕복이 추가된다. 

물론 이 네트워크를 왕복하는 시간 동안 다른 요청들도 전부 대기하게 된다.

물론 이외에도 분산락 자체가 어려운 문제다... 일반 서버에서도 넣기 어려워 꺼려지는 기능인데 Rate Limiter에 넣기에는 볼륨이 너무 크다.


#### 낙관락
Redis의 Watch와 Exec 명령어를 사용하는 방식.

트랜잭션을 시작하기 이전에 watch를 두고 마지막에 exec을 한다. 만약에 exec을 할 때 watch 때 와 값이 달라졌다면 watch 부터 exec까지의 모든 명령어를 실패로 돌린다. 그리고 재시도.

당연히 경합이 적은 상황에만 좋다.


## Synchronization

Rate Limiter가 병목지점이 되면 안되기에 대형 서비스들은 Rate Limiter도 클러스터로 구성해 사용하는 경우가 많다.

이 때, 각 서버에서 유저에 대한 한도 정보를 각자 가지고 있다면 서로 상태 공유가 안 된다.

분당 제한이 10이라고 하면 유저1이 A Rate Limiter에서 10, B Rate Limiter에서 10 사용해도 아무런 제한이 걸리지 않는다.

#### 중앙 집중형 저장소

이를 방지하기 위해 중앙 집중형 저장소를 둔다.

모든 Rate Limiter는 하나의 저장소(In-Memory)를 바라본다.

근데 여기서 Redis를 확장하면 문제가 된다.

Redis를 Master Slave로 나눴다고 해서 Master에는 쓰기, Slave에는 읽기를 시키면 복제 지연 때문에 오래된 값을 읽게 된다. 

Redis에서 Master Slave는 장애에 대한 빠른 대응과 데이터 유실을 줄이기 위함이지 읽기 부하 분산을 위함이 아니다.

방법은 샤딩이다. 

각 노드에 들어가는 키의 개수를 정해놓고, 특정 유저의 요청이 들어오면 유저에 해당하는 노드를 읽도록 하면 된다.
장애에 대해서는 Master Slave를 둬 수직적으로 대응한다.
![](asset/Pasted%20image%2020260828133126.png)


근데 Rate Limiter가 읽어내는 Redis를 굳이 이렇게까지 클러스터를 구성해야할지는 따져봐야한다.

Redis 단일 인스턴스는 초당 수십만 ops를 처리한다.

그리고 Rate Limiter의 연산은 INCR 몇 번이나 짧은 Lua 스크립트라 매우 가볍다.  초당 10만 요청 서비스라도 Redis 하나로 감당되는 경우가 많다.

정말 트래픽이 너무 많아서 감당이 안 된다면, 차라리 서비스 별로 Rate Limiter에 대한 Redis를 따로 두는 것도 방안이다.
