# 개요

> **처리율 제한 장치 = rate limiter**

클라이언트 또는 서비스가 보내는 트래픽의 처리율(rate)을 제어하기 위한 장치
> 

### 장점

- DoS(Denial of Service) 공격에 의한 자원 고갈 방지
- 비용 절감
    - 외부 API 사용 시 횟수당 과금이 이루어진다면 그 횟수를 제한해야 함
- 서버 과부하 방지
    - 봇 트래픽
    - 사용자의 잘못된 이용 패턴
    - …

### 위치

- 클라이언트
- 서비스 내부
- 미들웨어 형태(게이트웨이)

# 처리율 제한 알고리즘

- 토큰 버킷 (token bucket)
- 누출 버킷 (leaky bucket)
- 고정 윈도우 카운터 (fixed window counter)
- 슬라이딩 윈도우 로그 (sliding window log)
- 슬라이딩 윈도우 카운터 (sliding window counter)

## 토큰 버킷 알고리즘

> **토큰 버킷 = 지정된 용량을 갖는 컨테이너**

API 요청 하나당 토큰을 하나씩 가지고 사라짐
지정한 시간이 지나면 토큰이 리필됨
> 

통상적으로 API 엔드포인트마다 별도의 버킷을 둠

IP 주소별로 처리율 제한을 적용해야 한다면 IP 주소마다 버킷 할당

시스템 처리율을 가지고 제한을 두고 싶다면 모든 요청이 하나의 버킷을 공유하도록 해야 함

### **인자**

- 버킷 크기: 버킷에 담을 수 있는 토큰의 최대 개수
- 토큰 공급률(refill rate): 초당 몇 개의 토큰이 버킷에 공급되는가

### 프로세스

1. N개의 토큰으로 시작
2. 요청이 전달될 때마다 토큰 하나씩 소비
3. 토큰이 0개가 되면 요청 drop
4. 시간이 지나면 토큰 재공급
    1. 버킷 크기가 다 찼으면 토큰 버림

### 장점

- 구현이 쉬움
- 메모리 사용 측면에서 효율적
- 짧은 시간에 집중되는 트래픽 (traffic burst)도 처리 가능

### 단점

- 인자들의 값들을 적절하기 튜닝해야 하며 이 부분이 까다로움

## 누출 버킷 알고리즘

토큰 버킷 알고리즘과 유사하지만 요청 처리율이 고정되어 있음

일반적으로 FIFO(First-In-First-Out) 큐로 구현

### 인자

- 버킷 크기: 큐 사이즈와 동일 / 큐에는 처리될 요청들이 보관됨
- 처리율(overflow rate): 지정된 시간당 몇 개의 요청을 처리할지 지정 (일반적으로 초 단위)

### 프로세스

1. 요청 도착 시 큐가 가득 차 있는지 확인
    1. 큐에 자리가 있다면 큐에 요청 추가
    2. 큐에 자리가 없다면 요청 drop
2. 지정된 시간마다 큐에서 요청을 꺼내 처리

### 장점

- 큐의 크기가 제한되어 있어 메모리 사용량 측면에서 효율적
- 고정된 처리율을 가지고 있어서 안정적 출력이 필요한 경우 적합

### 단점

- 단시간에 많은 트래픽이 몰리는 경우 큐에 오래된 요청들이 쌓이게 됨
오래된 요청들을 시의성 있게 처리하지 못하면 최신 요청들이 버려지게 됨
- 토큰 버킷과 마찬가지로 두 개의 파라미터 값을 적절하게 튜닝해야 함

## 고정 윈도우 카운터

### 프로세스

1. 타임라인을 고정된 간격의 윈도우로 분할하고, 각 윈도우마다 카운터를 붙임
2. 요청이 접수될 때마다 카운터의 값을 1씩 증가
3. 카운터의 값이 사전에 설정된 임계치에 도달하면 새로운 요청은 새로운 윈도우가 열릴 때까지 drop

### 장점

- 메모리 효율이 좋음
- 이해가 편함

### 단점

- 윈도우 경계 부근에서 일시적으로 많은 트래픽이 발생하는 경우, 기대했던 시스템의 처리 한도보다 많은 양의 요청을 처리해야 하게 됨
ex. 분당 최대 N개의 요청만 처리해야 하는 시스템의 경우,
윈도우가 종료되는 시점에서 N개 이상의 트래픽 발생 + 그 다음 윈도우가 시작되는 시점에서 N개 이상의 트래픽 발생 → 윈도우의 타임라인을 조금만 옮겨보면 결국 2 * N 개의 요청이 1분동안 처리됨

## 슬라이딩 윈도우 로그

### 프로세스

1. 요청의 타임스탬프를 추적(일반적으로 Redis 또는 Sorted Set 등의 캐시에 저장)
2. 새 요청 발생 시 현재 윈도우의 시작 시점보다 오래된 타임스탬프 제거
3. 새 요청의 타임스탬프를 로그에 추가
    1. 로그의 크기가 허용치보다 같거나 작으면 요청을 시스템에 전달
    2. 아닌 경우엔 drop

**여기서 유의해야 할 점은 3번에서 drop 된 요청의 타임스탬프도 기록된다는 점이다.**

### 장점

- 어디서든 특정 구간의 윈도우를 봤을 때 허용되는 요청의 개수는 시스템의 처리율 한도를 넘기지 않음

### 단점

- drop 된 요청의 타임스탬프도 기록하기 때문에 메모리 사용량 ↑

## 슬라이딩 윈도우 카운터

고정 윈도우 카운터 + 슬라이딩 윈도우 로깅 알고리즘의 조합

### 계산 방식

현재 1분간의 요청 수 + 직전 1분간의 요청 수 * 슬라이딩 윈도우와 직전 1분이 겹치는 비율

### 장점

- 이전 시간대의 평균 처리율에 따라 현재 윈도우의 상태를 계산
→ 짧은 시간에 몰리는 트래픽에 대응 용이
- 메모리 효율이 좋음

### 단점

- 직전 시간대에 도착한 요청이 균등하게 분포되어 있다고 가정한 상태에서 추정치를 계산하기 때문에 다소 느슨함

# 카운터 보관

일반적으로 메모리상에서 동작하는 캐시(ex. Redis) 사용

Redis에는 아래 명령어 지원

- INCR: 메모리에 저장된 카운터의 값을 1만큼 증가
- EXPIRE: 카운터에 타임아웃 값 설정 → 시간이 지나면 카운터 자동 삭제

### 프로세스

1. 클라이언트가 처리율 제한 미들웨어에 요청 전송
2. 미들웨어는 레디스의 버킷에서 카운터를 가져와서 한도 도달 여부 체크
    1. 도달 시 요청 drop
    2. 도달하지 않았다면 API 서버로 요청 전달 및 카운터의 값을 증가시켜서 레디스에 저장

# 상세 설계

## 처리율 제한 규칙

일반적으로 설정 파일(configuration file) 형태로 디스크에 저장

## 처리율 한도 초과 트래픽의 처리

429 Response (too many requests) 전송

경우에 따라서 한도 제한에 걸린 메세지를 나중에 처리하기 위해 큐에 보관할 수도 있음

HTTP 응답 헤더에 처리율 제한에 관한 정보를 넣어서 응답할수도 있음

- X-Ratelimit-Remaining: 윈도우 내에 남은 처리 가능 요청의 수
- X-Ratelimit-Limit: 매 윈도우마다 클라이언트가 전송할 수 있는 요청의 수
- X-Ratelimit-Retry-After: 한도 제한에 걸리지 않으려면 몇 초 뒤에 요청을 다시 보내야 하는지 알림

## 분산 환경에서의 처리율 제한

고려해야 할 점

- 경쟁 조건(race condition)
- 동기화(synchronization)

### 경쟁 조건

두 요청이 거의 동시에 왔을 경우, 경쟁 조건 문제가 발생할 수도 있음

일반적으로 lock으로 해결 가능하지만, 성능 저하 문제 발생

#### 해결책

- 루아 스크립트(Lua script)
    - 한번에 여러개의 Redis 명령을 원자적으로 실행 가능하도록 함
- 정렬 집합(sorted set) 자료구조 사용

### 동기화 이슈

여러 대의 처리율 제한 장치 서버를 두게 되면 각 서버들간의 동기화 필요

sticy session 을 활용해 같은 클라이언트로부터의 요청은 항상 같은 처리율 제한 장치로 보내도록 할수도 있긴 한데 비추
→ 확장 가능한 아키텍처가 아니고 유연하지도 않음

그냥 Redis 쓰는게…

### 성능 최적화

- 엣지 서버 활용
- 제한 장치 간 데이터 동기화 시 최종 일관성 모델 사용
→ 6장에서 추가 설명

### 모니터링

고려해야 될 점

- 채택된 처리율 제한 알고리즘이 효과적인가
- 정의한 처리율 제한 규칙이 효과적인가

# 생각해봐야할 점

- 경성(hard) or 연성(soft) 처리율 제한
    - 경성 처리율 제한: 요청 개수는 임계치를 절대로 넘을 수 없다.
    - 연성 처리율 제한: 요청 개수는 잠시 동안은 임계치를 넘어설 수 있다.
- 다양한 계층에서의 처리율 제한
    - 책에서는 OSI 7계층 기준 애플리케이션 계층에 대한 처리율 제한만 살펴봤지만, 다른 계층에서의 처리율 제한도 가능하다.
    ex. Iptables를 사용한 IP 주소에 처리율 제한 적용
- 처리율 제한 회피 방법
    - 클라이언트 측 캐시를 사용해 API 호출 횟수를 줄인다.
    - 처리율 제한의 임계치를 이해하고, 짧은 시간 동안 너무 많은 요청을 보내지 않도록 한다.
    - 예외나 에러를 처리하는 코드를 도입해 클라이언트가 예외적인 상황으로부터 우아하게(gracefully) 복구될 수 있도록 한다.
    - 재시도(retry) 로직을 구현할 때는 충분한 백오프(back-off) 시간을 둔다.
