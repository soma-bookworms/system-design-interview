01요구사항 확정

면접관과 나눈 질의응답으로 다음 요구사항을 확정한다. 하루 백만 건 이상을 처리하는 시스템이라 요구사항을 먼저 좁힌다.

항목내용
알림 종류푸시 알림, SMS 메시지, 이메일
실시간성연성 실시간(soft real-time) 시스템. 높은 부하에서는 약간의 지연을 허용한다.
지원 단말iOS 단말, 안드로이드 단말, 랩톱과 데스크톱
알림 생성 주체클라이언트 애플리케이션과 서버 측 스케줄링
수신 거부수신 거부(opt-out)를 마친 사용자에게는 더 이상 보내지 않는다.
일일 발송량모바일 푸시 알림 천만 건, SMS 메시지 백만 건, 이메일 5백만 건

02알림 유형별 지원 방안

iOS 푸시 알림

세 가지 구성 요소가 필요하다. 알림 제공자는 알림 요청을 만들어 애플 푸시 알림 서비스(APNS)로 보내는 주체다. 요청을 만들려면 단말 토큰과 페이로드가 있어야 한다. 단말 토큰은 알림 요청을 보내는 데 필요한 고유 식별자이고, 페이로드는 알림 내용을 담은 JSON 딕셔너리다.

{
  "aps": {
    "alert": {
      "title": "Game Request",
      "body": "Bob wants to play chess",
      "action-loc-key": "PLAY"
    },
    "badge": 5
  }
}

APNS는 애플이 운영하는 원격 서비스로 푸시 알림을 iOS 장치까지 보내는 역할을 맡는다. iOS 단말은 푸시 알림을 수신하는 사용자 단말이다.

안드로이드 푸시 알림

절차는 iOS와 같고 APNS 대신 FCM(Firebase Cloud Messaging)을 사용한다.

SMS 메시지

트윌리오(Twilio)나 넥스모(Nexmo) 같은 제3자 사업자의 서비스를 주로 이용한다. 대부분 상용 서비스라 이용 요금을 낸다.

이메일

대부분의 회사는 고유 이메일 서버를 구축할 역량을 갖추고 있다. 그럼에도 센드그리드(Sendgrid)나 메일침프(Mailchimp) 같은 상용 서비스를 쓰는 회사가 많다. 전송 성공률이 높고 데이터 분석 기능도 함께 쓸 수 있기 때문이다.

03연락처 정보 수집 절차

알림을 보내려면 모바일 단말 토큰과 전화번호, 이메일 주소가 있어야 한다. 사용자가 앱을 설치하거나 처음으로 계정을 등록하면 API 서버가 해당 정보를 수집해 데이터베이스에 저장한다.

이메일 주소와 전화번호는 user 테이블에 저장하고 단말 토큰은 device 테이블에 저장한다. 사용자 한 명이 단말 여러 대를 가질 수 있고, 알림은 모든 단말에 전송해야 한다는 점을 고려한 구조다.

emailvarchar

device
idbigint
device_tokenvarchar
user_idbigint
last_logged_in_attimestamp

04알림 전송 및 수신 절차

개략적 설계안 초안

  • 1부터 N까지의 서비스: 마이크로서비스나 크론잡, 분산 시스템 구성 요소다. 납기일을 알리는 과금 서비스나 배송 알림을 보내는 쇼핑몰이 그 예다.
  • 알림 시스템: 알림 전송과 수신 처리의 핵심이다. 우선 서버 한 대만 사용한다고 가정한다. 서비스 1~N에 알림 전송용 API를 열어주고 제3자 서비스에 전달할 페이로드를 만든다.
  • 제3자 서비스: 사용자에게 알림을 실제로 전달한다. 통합할 때 유의할 점은 확장성이다. 새로운 서비스를 쉽게 붙이거나 뗄 수 있어야 한다. 어떤 서비스는 다른 시장에서 쓸 수 없다. FCM은 중국에서 사용할 수 없어 중국 시장에서는 제이푸시(Jpush)나 푸시와이(PushY)를 쓴다.
  • iOS/안드로이드/SMS/이메일 단말: 사용자는 자기 단말에서 알림을 수신한다.
문제내용
SPOF알림 서비스에 서버가 하나뿐이라 그 서버에 장애가 생기면 전체 서비스의 장애로 이어진다.
규모 확장한 대가 푸시 알림에 관계된 모든 것을 처리하므로 데이터베이스나 캐시 같은 중요 구성 요소의 규모를 개별적으로 늘릴 방법이 없다.
성능 병목알림을 처리하고 보내는 일은 자원을 많이 쓴다. HTML 페이지를 만들고 제3자 서비스의 응답을 기다리는 데 시간이 걸리므로, 모든 것을 한 서버로 처리하면 사용자 트래픽이 몰리는 시간에 과부하 상태에 빠진다.

개선된 설계안

  1. 데이터베이스와 캐시를 알림 시스템의 주 서버에서 분리한다.
  2. 알림 서버를 증설하고 자동으로 수평적 규모 확장이 이루어지도록 한다.
  3. 메시지 큐를 이용해 시스템 구성 요소 사이의 강한 결합을 끊는다.
  • 알림 서버: 네 가지 일을 맡는다. 알림 전송 API 운영과 알림 검증, 캐시나 데이터베이스 질의, 큐 적재다. 알림 전송 API는 스팸 방지를 위해 보통 사내 서비스나 인증된 클라이언트만 이용할 수 있다. 알림 검증은 이메일 주소와 전화번호를 기본적으로 검사하는 단계다. 큐 적재는 알림 데이터를 메시지 큐에 넣는 일이다. 큐를 종류별로 두므로 알림을 병렬로 처리한다.
  • 캐시: 사용자 정보, 단말 정보, 알림 템플릿을 캐시한다.
  • 데이터베이스: 사용자와 알림, 설정 정보를 저장한다.
  • 메시지 큐: 구성 요소 간 의존성을 제거하고, 다량의 알림이 전송되어야 하는 경우 버퍼 역할도 한다. 알림 종류별로 큐를 따로 두어 제3자 서비스 하나에 장애가 생겨도 다른 종류의 알림은 정상 동작한다.
  • 작업 서버: 메시지 큐에서 전송할 알림을 꺼내 제3자 서비스로 전달한다.

이메일 형태의 알림을 보내는 API 예시는 다음과 같다.

POST https://api.example.com/v/sms/send

{
  "to": [
    { "user_id": 123456 }
  ],
  "from": { "email": "from_address@example.com" },
  "subject": "Hello, World!",
  "content": [
    { "type": "text/plain", "value": "Hello, World!" }
  ]
}
단계동작
1API를 호출해 알림 서버로 알림을 보낸다.
2알림 서버가 사용자 정보, 단말 토큰, 알림 설정 같은 메타데이터를 캐시나 데이터베이스에서 가져온다.
3알림 서버가 전송할 알림에 맞는 이벤트를 만들어 해당 큐에 넣는다. iOS 푸시 알림 이벤트는 iOS 푸시 알림 큐에 넣는다.
4작업 서버가 메시지 큐에서 알림 이벤트를 꺼낸다.
5작업 서버가 알림을 제3자 서비스로 보낸다.
6제3자 서비스가 사용자 단말로 알림을 전송한다.

05안정성

데이터 손실 방지

알림 전송 시스템의 가장 중요한 요구사항은 어떤 상황에서도 알림이 소실되지 않는 것이다. 알림이 지연되거나 순서가 틀려도 괜찮지만 사라지면 곤란하다. 이 요구사항을 만족하려면 알림 데이터를 데이터베이스에 보관하고 재시도 메커니즘을 구현해야 한다. 알림 로그 데이터베이스를 유지하는 것이 한 가지 방법이다.

알림 중복 전송 방지

같은 알림이 여러 번 반복되는 것을 완전히 막기는 어렵다. 대부분의 경우 알림은 딱 한 번만 전송되지만, 분산 시스템의 특성상 가끔은 같은 알림이 중복되어 전송되기도 한다. 빈도를 줄이려면 중복을 탐지하는 메커니즘을 도입하고 오류를 신중하게 처리해야 한다.

간단한 중복 방지 로직은 다음과 같다. 보내야 할 알림이 도착하면 그 이벤트 ID를 검사해 이전에 본 적이 있는 이벤트인지 살핀다. 중복된 이벤트라면 버리고, 그렇지 않으면 알림을 발송한다.

06추가 구성 요소

알림 템플릿

대형 알림 시스템은 하루에도 수백만 건 이상의 알림을 처리하는데 그 메시지 대부분은 형식이 비슷하다. 알림 템플릿은 인자나 스타일, 추적 링크만 조정하면 사전에 지정한 형식에 맞춰 알림을 만들어 내는 틀이다. 템플릿을 쓰면 전송되는 알림들의 형식을 일관성 있게 유지하고 오류 가능성과 작성 시간을 함께 줄인다.

본문
여러분이 꿈꿔온 그 상품을 우리가 준비했습니다. [item_name]이 다시 입고되었습니다! [date]까지만 주문 가능합니다!

타이틀(CTA: Call to Action)
지금 [item_name]을 주문 또는 예약하세요!

알림 설정

사용자는 이미 너무 많은 알림을 받고 있어서 쉽게 피곤함을 느낀다. 따라서 많은 웹사이트와 앱에서는 사용자가 알림 설정을 상세히 조정할 수 있도록 한다. 이 정보는 알림 설정 테이블에 보관하며 다음과 같은 필드를 둔다.

필드타입설명
user_idbigInt사용자 식별자
channelvarchar알림이 전송될 채널. 푸시 알림, 이메일, SMS 등
opt_inboolean해당 채널로 알림을 받을 것인지의 여부

이 설정을 도입한 뒤에는 특정 종류의 알림을 보내기 전에 반드시 해당 사용자가 해당 알림을 켜 두었는지 확인해야 한다.

전송률 제한

사용자에게 너무 많은 알림을 보내지 않도록 하는 한 가지 방법은 한 사용자가 받을 수 있는 알림의 빈도를 제한하는 것이다. 알림을 너무 많이 보내면 사용자가 알림 기능을 아예 꺼 버릴 수도 있다.

재시도 방법

제3자 서비스가 알림 전송에 실패하면 해당 알림을 재시도 전용 큐에 넣는다. 같은 문제가 계속해서 발생하면 개발자에게 통지한다.

푸시 알림과 보안

iOS와 안드로이드 앱의 경우 알림 전송 API는 appKey와 appSecret을 사용해 보안을 유지한다. 따라서 인증된 클라이언트나 승인된 클라이언트만 해당 API로 알림을 보낼 수 있다.

큐 모니터링

알림 시스템을 모니터링할 때 중요한 지표는 큐에 쌓인 알림의 개수다. 이 수가 너무 크면 작업 서버들이 이벤트를 빠르게 처리하지 못한다는 뜻이다. 그런 경우에는 작업 서버를 증설하는 것이 바람직하다.

이벤트 추적

알림 확인율, 클릭율, 실제 앱 사용으로 이어지는 비율 같은 지표는 사용자를 이해하는 데 중요하다. 데이터 분석 서비스는 보통 이벤트 추적 기능도 갖추고 있어서 알림 시스템을 만들면 데이터 분석 서비스와도 통합해야 한다.

07수정된 설계안

추가된 것내용
인증, 전송률 제한알림 서버에 인증(authentication)과 전송률 제한(rate-limiting) 기능을 더했다.
재시도전송 실패에 대응하는 기능이다. 전송에 실패한 알림은 다시 큐에 넣고 지정된 횟수만큼 재시도한다.
전송 템플릿알림 생성 과정을 단순화하고 알림 내용의 일관성을 유지한다.
모니터링과 추적시스템 상태를 확인하고 추후 시스템을 개선하기 쉽도록 한다.

08마무리

이번 장에서는 규모 확장이 쉬울 뿐 아니라 푸시 알림, SMS 메시지, 이메일 등 여러 정보 전달 방식을 지원하는 알림 시스템을 만들었다. 시스템 구성 요소 사이의 결합도를 낮추기 위해 메시지 큐를 적극적으로 사용하였다. 집중한 주제는 다음과 같다.

주제내용
안정성메시지 전송 실패율을 낮추기 위해 안정적인 재시도 메커니즘을 도입하였다.
보안인증된 클라이언트만 알림을 보낼 수 있도록 appKey와 appSecret 등의 메커니즘을 이용하였다.
이벤트 추적과 모니터링알림이 만들어진 후 성공적으로 전송되기까지의 과정을 추적하고 시스템 상태를 모니터링하기 위해 전송 단계마다 이벤트를 추적하고 모니터링하는 시스템을 통합하였다.
사용자 설정사용자가 알림 수신 설정을 조정할 수 있도록 하였다. 따라서 알림을 보내기 전에 반드시 해당 설정을 확인하도록 시스템 설계를 변경하였다.
전송률 제한사용자에게 알림을 보내는 빈도를 제한할 수 있도록 하였다.
