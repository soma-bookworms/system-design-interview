# 요구사항
---
1. 알림 채널 : 푸시알림, SMS , 이메일
2. 실시간성 : Soft Real Time - 실시간성이 있어야하지만 부하가 높을 때 약간의 지연은 허용된다.
3. 지원단말 : iOS, Android, 데스크탑
4. 알림 생성 주체 : 클라이언트 요청, 서버 스케줄링
5. 수신거부 : 수신거부 설정한 사용자에게는 발송되지 않음
6. 일일 발송량 : 모바일 푸시 1000만 건, SMS 100만 건, 이메일 500만 건

일일 발송량은 이렇지만, 초당 평균으로 계산할 것이 아니라 아마 좁은 시간대에 몰려있을 확률이 큼


# 알림 발송 상황 유형
---
1. 즉시 알림
	- 배달의 민족 배달 시작 안내, 결제 완료 안내, 회원가입 인증번호 
	- 사용자가 행동을 하고 직후에 알림을 보내줘야함. 
	- 지연은 거의 허용되지 않음 (수 초)
	- 유실방지, 우선처리
2. 상호작용 알림
	- 인스타그램 좋아요 댓글, 카카오톡 메세지 
	- 사용자 행동 직후
	- 지연 어느정도 허용됨 (수십 초)
	- 묶음 발송
3. 예약 알림
	- 장바구니에 담아둔 상품 안내, 숙소 예약 알림, 듀오링고 학습 알림
	- 사용자마다 발송여부, 혹은 발송 시간이 다름.
	- 지연은 상황마다 다르지만 수십초 에서 수 분 정도 허용 가능
	- 발송 조건, 발송 시간 확인이 중요
4. 대량발송 홍보 알림
	- 할인쿠폰, 앱 공지
	- 운영자가 정한 시간
	- 수십분의 지연도 허용 가능할 듯
	- 이 알림으로 인해서 다른 알림에 부하가 생기면 안됨. 

분류해보면
- 이벤트형 (클라이언트 생성)
	- 즉시 알림, 상호작용 알림
- 스케줄형 (서버 생성)
	- 예약 알림, 대량발송 홍보 알림

#  알아두면 좋은점
#### MQ의 At Most Once, At Least Once, Exactly Once
메세지의 보장수준과 신뢰성
- At Most Once : 처리하기전에 커밋하거나 메세지를 지우는 방식 -> 처리 도중에 consumer가 죽으면 이미 커밋 명령을 큐에 보냈으므로 큐는 해당 메세지가 처리된 것으로 인지하고 삭제한다. 
- At Least Once : 처리하고나서 커밋하거나 메세지를 지우는 방식. -> 처리 도중에 consumer가 죽으면 아직 커밋 명령을 큐에 안 보냈으므로 큐는 해당 메세지가 처리 안 된 것으로 인식한다. 
- Exactly Once :  정확히 한번만 처리되는 방식 -> Consumer 혹은 저장소 등에서 단독으로 처리 여부에 대한 중복을 알아채고 중복 메세지를 버려줘야함.

ACK과 Commit
![[알림시스템-ack-커밋.svg]]
MQ마다 다르지만 kafka를 기준으로 설명하자면,,
ACK
- ACK=0 : 메세지브로커의 응답을 아예 안기다림. 네트워크로 내보내는순간 성공으로보고 다음 메세지를 적재함. 빠르지만 브로커가 받았는지 모르므로 유실을 감지하거나 재시도가 불가능하다.
- ACK=1 : 리더 브로커(클러스터링 가정)가 자기 로그에 쓰고 응답. 대부분 안전하지만 리더브로커가 레플리카들한테 넘기기전에 죽으면 유실
- ACK=2 : 동기화된 레플리카 전부가 쓴 뒤에 응답한다. 여기에서 몇 개의 레플리카에 복제됐을 때 완료로 볼지는 설정 가능
Commit
- Auto Commit : 설정 시간마다 메세지를 consume 할 때 직전에 consume 한 오프셋이 커밋된다. 그냥 일정 시간마다 완료된 메세지들을 갱신해주는 방식
- Manual Commit : 사용자가 직접 커밋을 어떻게할지 코드로 풀어냄 이 안에 동기 커밋과 비동기 커밋도 있음. 동기 커밋은 커밋 후에 브로커의 응답을 기다리고 비동기는 그냥 콜백으로만 받음.

#### AWS SNS
AWS SNS는 2010년에 출시한 (pub/sub) 메세징 서비스다.
서비스를 이용하면 푸시알림을 보낼 때 편한게 몇가지 있다.
1. 플랫폼 인증 대신 - APNs 키, FCM 계정키 둘 다 올려두면 APNs 용 JWT 서명이나 구글 OAuth 토큰 발급을 알아서 해줌. 키 관리와 토큰 갱신 로직이 필요없음.
2. 단말토큰마다 ARN이 하나생기고 엔드포인트로 감싸게됨. 전송시 토큰 대신 그 ARN을 지정하고 토큰이 유효하지 않을경우 SNS가 해당 ARN을 비활성으로 바꿔줌. 토큰을 직접 지우는 일을 안 해도 됨.
3. 엔드포인트들을 토픽에 구독시켜두면 한번 publish 할 경우 구독자 전체에게 나간다. 전체 공지 처럼 같은 내용을 모두에게 보낼 때 요청 수 한번에 SNS에서 구독되어있는 모든 사용자에게 알아서 뿌려준다.
4. 전달 큐 -> APNs, FCM 사이의 오류 재시도를 알아서 해줌. SQS 연결하면 DLQ도 가능
다만 생각보다 활용할 곳이 많진 않을 수 있음.
